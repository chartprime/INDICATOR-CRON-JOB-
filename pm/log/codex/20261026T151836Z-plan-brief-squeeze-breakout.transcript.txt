# Build brief: Squeeze Breakout Context (draft for Codex plan round 1)

Drafted by the OHLCV specialist for the PM. Shared rules: `PM/WORKER-BRIEF.md`,
`PM/CAPABILITIES.md`, `PM/cycle1/ux-standard.md` (binding), 
`PM/cycle1/validation-protocol.md`. Structure and rigour follow
`PM/cycle1/brief-rvol-clock.md` as approved after five plan rounds.

## The trading question

"Is price coiled right now, which way does the surrounding trend lean, and
when the coil breaks, did the break bar carry range and volume, or did price
fall back inside?"

## Target user and decision

Intraday and swing breakout traders on BTC, ETH, ES, NQ, AAPL, TSLA. Decision:
treat a close outside the compression range as a break worth acting on, as a
trap once it fails, or as counter-trend context. Descriptive only: it names the
range, the side the trend favours and what the break bar did; it does not
predict follow-through, and the package says so.

## Identity

- Folder `apps/web/src/lib/indicators/squeeze-breakout/`; def
  `squeezeBreakout.ts`; pure state machine in `squeezeBreakoutMath.ts`;
  tests in `tests/`.
- id `squeezeBreakout`, label `"Squeeze Breakout (20)"`, category
  `"technical"`, placement `{ kind: "overlay" }`, `maxReplayBars` 3,000.
- Historical Mode policy `OHLCV_POLICY`: reads `bar.high/low/close/volume`,
  `bar.ts_open`, `bar.interval_ms`, `bar.closed` only. Works on every archived
  instrument and on equities (volume is unsided-agnostic; no `barSides`).
- No `timeframeGate`; every timeframe is supported.

## Data and library use

`ta.bollinger(len, bbMult)` on close and `ta.keltner(len, len, kcMult)` on
`{high, low, close}` give the squeeze state; `ta.ema(50)` and `ta.ema(200)` on
close give the bias. These four library streams are pushed with `replace`.
Documented limitation: a bar superseded without ever closing stays in them at
its last values (the library cannot retract an input), so the squeeze flag and
bias are "as the chart showed them", while every value that enters an event
(box edges, denominators) is own state and excludes such bars.

The volume and range denominators use the ring primitives exported by
`relative-volume/relativeVolumeMath.ts` (`createRing`, `ringInsert`,
`ringUpdate`, `ringRemove`, `ringSupersede`, `ringMean`), capacity 20, keyed
by `ts_open`, with the same tail-only correction and eviction rollback
semantics that module already proves. **The slot-median (time-of-day) baseline
is not used in this version**: it needs three prior sessions per minute, so the
grade would be `null` for three days on a fresh symbol and on every 400-bar
labelled fixture, untestable on labelled data and different in meaning from bar
to bar. A `volumeRule` (`rolling20` | `timeOfDay`) is a v2 Advanced option once
a multi-session breakout fixture exists (import `createRelativeVolumeEngine`,
read `reading.rvol`).

## Calculation (incremental, one dispatch at a time)

Terms: `len` 20, `bbMult` 2, `kcMult` 1.5, `minSqueezeBars` 6, `releaseBars`
3, `confirmMultiple` 1.5, `failBars` 5, `holdBars` 40.

1. **Tail record, keyed by `ts_open`.** The first dispatch of a new `ts_open`
   creates the record and snapshots, before any write, `boxAtOpen` (the
   committed box: `hi`, `lo`, `age`, `offRun`, `broken`), `avgRange20` (mean of
   the range ring) and `avgVolume20` (mean of the volume ring). Every later
   dispatch of the same `ts_open` (forming revision or closed correction)
   recomputes the tail's decision from these snapshots and the tail's current
   values; the tail never sees itself in a denominator or in the box it is
   tested against.
2. **Time gap.** If `ts_open − previousCommitted.ts_open > interval_ms`, the
   committed box is discarded before the snapshot (the coil's context is
   stale across a hole or an equity overnight) and the status row shows
   `Gap · box reset` on that bar. Streams and rings continue.
3. **Squeeze flag.** Push the bar into bollinger and keltner. `squeezeOn` =
   `bbUpper < kcUpper && bbLower > kcLower`; `depth = (bbUpper − bbLower) /
   (kcUpper − kcLower)`, `null` when either stream is `null` or the KC width is
   0. (The baseline uses `ta.ttmSqueeze` for the same definition, so the two
   are independent implementations.)
4. **Box test (read).** If `boxAtOpen` exists, is not broken and `age ≥
   minSqueezeBars`: `breakDir` = +1 if `close > hi`, −1 if `close < lo`, else
   0. On a break: `expansion = trueRange ≥ confirmMultiple × avgRange20`,
   `volume = bar.volume ≥ confirmMultiple × avgVolume20`; grade `confirmed`
   (both), `partial` (one), `unconfirmed` (none); a `null` denominator makes
   the flag false and the grade carries `denominatorMissing`. True range uses
   the previous committed close.
5. **Failure test (read).** If `boxAtOpen.broken` is set: `close` back inside
   `[lo, hi]` of the frozen box marks `failed`; otherwise, when `index −
   brokenIndex ≥ failBars`, the break is complete and the box is retired.
6. **Commit (write), only on the first dispatch with `closed === true`.**
   In order: (a) range and volume enter their rings (`ringInsert`); (b) if no
   box exists and `squeezeOn`, open one with this bar's `high/low`, `age` 1;
   (c) else if a box exists and is not broken, extend `hi/lo` with this bar,
   then `age += 1, offRun = 0` if `squeezeOn`, else `offRun += 1`, and
   `offRun > releaseBars` discards the box (no event); (d) on a break the box
   freezes (`hi/lo` stop extending) and `broken = {index, dir, grade}`;
   excursion extremes are tracked separately; (e) on a failure the box widens
   to the excursion extremes and re-arms with its age kept; (f) on a completed
   break the box is retired and, if `squeezeOn` still holds, a new box opens
   on the next closed bar with `age` 1 (the coil continues). A squeeze shorter
   than `minSqueezeBars` that releases yields no event and no box is kept.
7. **Superseded without close.** A tail superseded by a newer `ts_open` while
   `closed === false` writes nothing: no ring entry, no box change, no event;
   its provisional marker is removed on the next dispatch. Missing data
   contributes nothing.
8. **Corrections are tail-only.** A closed re-dispatch of the tail with
   different values recomputes the decision from the snapshots, `ringUpdate`s
   both rings, and rebuilds the committed box as `boxAtOpen` plus this bar; a
   valid-to-invalid correction (`volume` not finite or ≥ 0, prices not finite)
   `ringRemove`s and restores `evictedByTail`. An older correction reaches the
   indicator as `REBUILT` and recreates state. `ringSupersede` runs when the
   tail is superseded.
9. **Bias.** `up` if `close > ema200` and `ema50 > ema50 five committed bars
   earlier` (own 6-entry ring of committed ema50 values); `down` on the mirror;
   else `neutral`; `unknown` while either EMA is `null`. Re-evaluated every
   dispatch; it colours the box and the table, and never gates an event.
10. **Outputs** (`readOutput`): `boxHigh`, `boxLow` (`null` with no armed,
    broken or held box), `depth`, `squeezeOn` 0/1, `bias` −1/0/1 (`null`
    unknown), `breakDir` −1/0/1, `breakGrade` 0 none, 1 unconfirmed, 2 partial,
    3 confirmed, `failed` 0/1, `boxAge`. `boxHigh`/`boxLow` are the two line
    outputs; the rest are numeric seams.
11. **Status precedence, first match wins.** `Warming up · n of 21 bars`
    (rings and bands need 20 committed bars plus one); `Gap · box reset`;
    `Failed break · re-armed`; `Break ↑ · confirmed` / `partial` /
    `unconfirmed` (↓ for down) while a break is pending or on its bar;
    `Squeeze · 9 bars · 0.72`; `Squeeze paused · 1 of 3`; `No squeeze`.
    Second row: `Bias up · EMA 50/200`, `Bias down`, `Bias neutral`, `Bias ·
    warming 120 of 200`. Third row: `Last · break ↑ 12:34 · confirmed` or `—`.
    Forming tail: same strings, provisional styling (50 percent alpha).
12. **No future data; fail closed.** Every value at bar t uses bars with
    `ts_open ≤ t.ts_open`; any non-finite intermediate yields `null`.

## Default view

Overlay. One translucent box per coil from its first bar to the current bar
(`draw.box` pool of 8 handles from `createState`, mutated per bar, skipped
when `drawNow === false`): fill 0.12 alpha, border 1 px, colour by bias (house
bull / bear pair; purple `#8672b3` for neutral or unknown). A broken box stops
at the break bar and is held `holdBars` bars at 0.06 alpha; a failed box's
border turns `--warn`. The `boxHigh`/`boxLow` lines (width 1, bias colour)
give the harness its outputs and the trader the exact edges. Table, top right,
three rows as in rule 11. Nothing drawn before warm-up; never a zero.

## Alert conditions (markers plus table)

Two event types, the UX maximum: **Break** — `arrowUp` below the bar (up) or
`arrowDown` above it (down), drawn only for `confirmed` (solid) and `partial`
(50 percent alpha) grades, bull/bear colour; unconfirmed breaks are table and
box only. **Failed break** — `circle`, `inBar`, `--warn`, only for a break
that was marked. Markers are a pure function of the bar's current decision:
a forming bar's marker is provisional and revised on each replace; a closed
correction that changes the grade adds or removes it; a duplicate closed
dispatch changes nothing.

## Limitations to state

Descriptive, not predictive. Warm-up 21 bars; bias needs 200. The squeeze
flag can include a never-closed bar's last values. Continuation squeezes in a
strong trend produce repeated with-bias boxes. A tall first bar makes a tall
box. Equity overnight gaps reset the box, so an opening-drive break is not
graded. Unit-free; no sided volume.

## Seams for L1 and L2 (named, not built)

`readOutput` keys `boxHigh`, `boxLow`, `breakDir`, `breakGrade`, `failed`
and `boxAge` are the contract: an L1 tape tally grades trade intensity on the
`breakDir` bar; the L2 Break Defense Monitor watches displayed liquidity at
`boxHigh`/`boxLow` while `boxAge ≥ minSqueezeBars`. Shared through
`squeezeBreakoutMath.ts` as a module, not a runtime link; any combined score
is its own brief with its own validation.

## Budget

One build run, UX joins before the end, at most two fix rounds after Codex
code review and validation; a third failure returns the concept to the backlog.

## Ten-line summary

1. Overlay box over a Bollinger-inside-Keltner squeeze, from committed bars only.
2. Box coloured by EMA 50/200 bias; bias never gates an event.

import type { BarFrame } from "../../../types/frames";
import { nyLocalMinuteOfDay } from "../killzones/killzones";

/**
 * Relative Volume by Time of Day: the pure, incremental machinery.
 *
 * One observation per committed bar is filed under the bar's start minute of
 * day (the "slot key") in a ring of the last `sessions` observations, and in a
 * second ring of the last 20 committed bars. A bar's ratio divides its volume
 * by the slot ring's median read *before* the bar's own observation entered
 * the ring (`baselineAtOpen`), so a bar never sees itself in its denominator
 * and every later revision of that bar divides by the same number.
 *
 * Corrections are tail-only: a closed dispatch of the newest bar with a
 * different volume updates the observation in place, a valid-to-invalid
 * correction removes it (restoring whatever its insertion evicted), and
 * invalid-to-valid re-inserts it. A correction to any older bar reaches the
 * indicator as a full replay, which recreates this state from scratch.
 *
 * Only a closed bar is ever filed. A bar that is superseded by a newer bar
 * without ever closing (a close that never arrived, a resampled bucket cut
 * short by a source gap) contributes no observation to either ring and its
 * own reading stays provisional: missing data contributes nothing.
 *
 * Exported so that a later indicator (Squeeze Breakout Context) can import the
 * slot-median machinery as its volume confirmation.
 */

export const MINUTE_MS = 60_000;
export const HOUR_MS = 3_600_000;
export const DAY_MS = 86_400_000;
export const MINUTES_PER_DAY = 1_440;
/** Time of day needs an intraday bar: anything longer than one hour yields null. */
export const RVOL_MAX_INTERVAL_MS = HOUR_MS;
export const RVOL_ROLLING_LENGTH = 20;
export const RVOL_DEFAULT_SESSIONS = 10;
/** Three, not two: with two observations the even-count median is a mean, and one news day would halve tomorrow's ratio. */
export const RVOL_MIN_SESSIONS_SETTING = 3;
export const RVOL_MAX_SESSIONS_SETTING = 60;
export const RVOL_DEFAULT_MIN_SESSIONS = 3;

export type RvolClock = "auto" | "newYork" | "utc";
export type ResolvedRvolClock = "newYork" | "utc";

export interface RelativeVolumeMathSettings {
  /** Ring capacity per slot key: the last N matching bars (3..60). */
  sessions: number;
  /** Prior observations a slot needs before a ratio is shown; clamped to `sessions` at read time. */
  minSessions: number;
  clock: RvolClock;
}

/** `auto` is New York for the dxFeed and Databento providers and UTC for Binance. */
export function resolveRvolClock(clock: RvolClock, provider: BarFrame["provider"]): ResolvedRvolClock {
  if (clock === "newYork" || clock === "utc") return clock;
  return provider === "DXFEED" || provider === "DATABENTO" ? "newYork" : "utc";
}

/**
 * One-entry cache of the New York minute at the start of a UTC hour. The New
 * York offset is constant inside any UTC hour (both DST changes fall on an
 * hour boundary), so a chronological series needs one `Intl` call per hour.
 */
export interface ClockCache {
  hourStart: number;
  minuteAtHourStart: number;
}

export function createClockCache(): ClockCache {
  return { hourStart: Number.NaN, minuteAtHourStart: 0 };
}

/** The bar's start minute of day (0..1439) in the resolved clock, or null for an unusable timestamp. */
export function slotKeyOf(tsOpen: number, clock: ResolvedRvolClock, cache?: ClockCache): number | null {
  if (!Number.isSafeInteger(tsOpen) || tsOpen < 0) return null;
  if (clock === "utc") return Math.floor((tsOpen % DAY_MS) / MINUTE_MS);
  const hourStart = Math.floor(tsOpen / HOUR_MS) * HOUR_MS;
  let minuteAtHourStart: number;
  if (cache !== undefined && cache.hourStart === hourStart) {
    minuteAtHourStart = cache.minuteAtHourStart;
  } else {
    minuteAtHourStart = nyLocalMinuteOfDay(hourStart);
    if (cache !== undefined) {
      cache.hourStart = hourStart;
      cache.minuteAtHourStart = minuteAtHourStart;
    }
  }
  return (minuteAtHourStart + Math.floor((tsOpen - hourStart) / MINUTE_MS)) % MINUTES_PER_DAY;
}

/** A finite volume at or above zero; anything else contributes no observation. */
export function usableVolume(volume: unknown): number | null {
  return typeof volume === "number" && Number.isFinite(volume) && volume >= 0 ? volume : null;
}

export interface Observation {
  tsOpen: number;
  volume: number;
}

export interface ObservationRing {
  readonly capacity: number;
  /** Oldest first; never longer than `capacity`. */
  readonly items: Observation[];
  /** What the newest insertion pushed out, kept until that tail is superseded so a correction can restore it. */
  evictedByTail: Observation | null;
}

export function createRing(capacity: number): ObservationRing {
  const size = Number.isFinite(capacity) ? Math.max(1, Math.floor(capacity)) : 1;
  return { capacity: size, items: [], evictedByTail: null };
}

export function ringInsert(ring: ObservationRing, observation: Observation): void {
  ring.items.push(observation);
  if (ring.items.length > ring.capacity) ring.evictedByTail = ring.items.shift() ?? null;
}

/** Changes the volume of the observation filed under `tsOpen` in place; false when none is filed. */
export function ringUpdate(ring: ObservationRing, tsOpen: number, volume: number): boolean {
  for (let index = ring.items.length - 1; index >= 0; index -= 1) {
    if (ring.items[index].tsOpen === tsOpen) {
      ring.items[index].volume = volume;
      return true;
    }
  }
  return false;
}

/** Removes the observation filed under `tsOpen` and restores what its insertion evicted. */
export function ringRemove(ring: ObservationRing, tsOpen: number): boolean {
  for (let index = ring.items.length - 1; index >= 0; index -= 1) {
    if (ring.items[index].tsOpen !== tsOpen) continue;
    ring.items.splice(index, 1);
    if (ring.evictedByTail !== null) {
      ring.items.unshift(ring.evictedByTail);
      ring.evictedByTail = null;
    }
    return true;
  }
  return false;
}

/** The tail that inserted into this ring has been superseded by a newer bar: its eviction is final. */
export function ringSupersede(ring: ObservationRing): void {
  ring.evictedByTail = null;
}

/** Median of the ring's volumes (mean of the two middle values for an even count); null when empty. */
export function ringMedian(ring: ObservationRing, scratch: number[] = []): number | null {
  const count = ring.items.length;
  if (count === 0) return null;
  scratch.length = count;
  for (let index = 0; index < count; index += 1) {
    // Insertion sort: the ring holds at most 60 values and this runs once per bar.
    const value = ring.items[index].volume;
    let position = index;
    while (position > 0 && scratch[position - 1] > value) {
      scratch[position] = scratch[position - 1];
      position -= 1;
    }
    scratch[position] = value;
  }
  const middle = count >> 1;
  const median = count % 2 === 1 ? scratch[middle] : (scratch[middle - 1] + scratch[middle]) / 2;
  return Number.isFinite(median) ? median : null;
}

export function ringMean(ring: ObservationRing): number | null {
  const count = ring.items.length;
  if (count === 0) return null;
  let sum = 0;
  for (let index = 0; index < count; index += 1) sum += ring.items[index].volume;
  const mean = sum / count;
  return Number.isFinite(mean) ? mean : null;
}

/** The slot ring capacity: `sessions` brought into 3..60. */
export function ringCapacityOf(settings: RelativeVolumeMathSettings): number {
  if (!Number.isFinite(settings.sessions)) return RVOL_DEFAULT_SESSIONS;
  return Math.min(RVOL_MAX_SESSIONS_SETTING, Math.max(RVOL_MIN_SESSIONS_SETTING, Math.floor(settings.sessions)));
}

export function requiredPriorOf(settings: RelativeVolumeMathSettings): number {
  const minimum = Number.isFinite(settings.minSessions) ? Math.floor(settings.minSessions) : RVOL_DEFAULT_MIN_SESSIONS;
  return Math.max(1, Math.min(minimum, ringCapacityOf(settings)));
}

function ratioOf(volume: number, denominator: number | null): number | null {
  if (denominator === null || !(denominator > 0)) return null;
  const ratio = volume / denominator;
  return Number.isFinite(ratio) ? ratio : null;
}

/** The reading for a tail record: rule 9 (outputs) and rule 11 (status precedence, first match wins). */
export function readingOf(tail: TailRecord, settings: RelativeVolumeMathSettings): RvolReading {
  const requiredPrior = requiredPriorOf(settings);
  const base = tail.baselineAtOpen;
  const reading: RvolReading = {
    tsOpen: tail.tsOpen,
    key: tail.key,
    volume: tail.volume,
    rvol: null,
    rolling: null,
    slotMeanRatio: null,
    priorCount: base.priorCount,
    rollingCount: base.rollingCount,
    requiredPrior,
    confirmed: tail.confirmed,
    status: "ready",
  };
  if (!tail.supported) {
    reading.status = "unsupported";
    return reading;
  }
  if (tail.volume === null) {
    reading.status = "noVolume";
    return reading;
  }
  reading.rolling = base.rollingCount >= RVOL_ROLLING_LENGTH ? ratioOf(tail.volume, base.rollingMean) : null;
  if (base.priorCount < requiredPrior) {
    reading.status = "learning";
    return reading;
  }
  reading.slotMeanRatio = ratioOf(tail.volume, base.slotMean);
  reading.rvol = ratioOf(tail.volume, base.slotMedian);
  if (reading.rvol === null) {
    reading.status = "noBaseline";
    return reading;
  }
  reading.status = tail.confirmed ? "ready" : "forming";
  return reading;
}

export function createRelativeVolumeEngine(settings: RelativeVolumeMathSettings): RelativeVolumeEngine {
  const capacity = ringCapacityOf(settings);
  const slots = new Map<number, ObservationRing>();
  const rolling = createRing(RVOL_ROLLING_LENGTH);
  const clockCache = createClockCache();
  const scratch: number[] = [];
  let tail: TailRecord | null = null;
  let current: RvolReading | null = null;

  function slotFor(key: number): ObservationRing {
    let ring = slots.get(key);
    if (ring === undefined) {
      ring = createRing(capacity);
      slots.set(key, ring);
    }
    return ring;
  }

  function readBaseline(key: number | null): BaselineAtOpen {
    const slot = key === null ? undefined : slots.get(key);
    return {
      slotMedian: slot === undefined ? null : ringMedian(slot, scratch),
      slotMean: slot === undefined ? null : ringMean(slot),
      priorCount: slot === undefined ? 0 : slot.items.length,
      rollingMean: ringMean(rolling),
      rollingCount: rolling.items.length,
    };
  }

  /** Rule 7(a): the commit event for the tail on its first closed dispatch, filing its volume when it is usable. */
  function commit(record: TailRecord): void {
    record.committed = true;
    if (!record.supported || record.key === null || record.volume === null) return;
    const observation = { tsOpen: record.tsOpen, volume: record.volume };
    ringInsert(slotFor(record.key), observation);
    ringInsert(rolling, { tsOpen: record.tsOpen, volume: record.volume });
    record.inRings = true;
  }

  /** A later dispatch of a committed tail: update in place, remove (valid to invalid) or insert (invalid to valid). */
  function reconcile(record: TailRecord): void {
    if (!record.supported || record.key === null) return;
    const slot = slotFor(record.key);
    if (record.volume !== null && record.inRings) {
      ringUpdate(slot, record.tsOpen, record.volume);
      ringUpdate(rolling, record.tsOpen, record.volume);
    } else if (record.volume !== null) {
      ringInsert(slot, { tsOpen: record.tsOpen, volume: record.volume });
      ringInsert(rolling, { tsOpen: record.tsOpen, volume: record.volume });
      record.inRings = true;
    } else if (record.inRings) {
      ringRemove(slot, record.tsOpen);
      ringRemove(rolling, record.tsOpen);
      record.inRings = false;
    }
  }

  function supersede(record: TailRecord): void {
    if (record.key !== null) {
      const slot = slots.get(record.key);
      if (slot !== undefined) ringSupersede(slot);
    }
    ringSupersede(rolling);
  }

  function onBar(bar: BarFrame): RvolReading {
    const tsOpen = bar.ts_open;
    if (tail !== null && tsOpen < tail.tsOpen) {
      // A dispatch older than the current record: the runtime replays those, so here it is ignored.
      return current ?? readingOf(tail, settings);
    }
    if (tail === null || tsOpen > tail.tsOpen) {
      // A tail superseded without ever closing files nothing (rule 7(b) was withdrawn): only a closed bar is an observation.
      if (tail !== null) supersede(tail);
      const intervalOk = Number.isFinite(bar.interval_ms) && bar.interval_ms > 0 && bar.interval_ms <= RVOL_MAX_INTERVAL_MS;
      const key = intervalOk ? slotKeyOf(tsOpen, resolveRvolClock(settings.clock, bar.provider), clockCache) : null;
      tail = {
        tsOpen,
        key,
        supported: intervalOk && key !== null,
        volume: usableVolume(bar.volume),
        baselineAtOpen: readBaseline(key),
        committed: false,
        inRings: false,
        confirmed: false,
      };
    } else {
      tail.volume = usableVolume(bar.volume);
    }
    if (bar.closed === true) tail.confirmed = true;
    if (!tail.committed) {
      if (bar.closed === true) commit(tail); // rule 7(a)
    } else {
      reconcile(tail);
    }
    current = readingOf(tail, settings);
    return current;
  }

  return {
    settings,
    onBar,
    get current() {
      return current;
    },
    get tail() {
      return tail;
    },
    rollingRing: rolling,
    slotRing: (key) => slots.get(key),
    get slotCount() {
      return slots.size;
    },
  };
}

## 3. Execution model

- Incremental: `createState(settings)` once, `onBar(ctx)` per bar event. A
  forming bar is revised with `replace: true`, possibly many times per second.
  Never recompute from a history array.
- Full replay on activation, symbol/provider/timeframe switch, reconnect, and
  any `recompute` setting change. `maxReplayBars` bounds it.
- Fault latching: a throw, a non-finite number, or a non-string color disables
  the indicator until it is removed and re-added. Fail closed to `null`.
- `ta.*` (62 streaming factories: sma, ema, rsi, macd, atr, bollinger,
  keltner, adx, superTrend, ttmSqueeze, vwap, obv, mfi, stdev, highest,
  lowest, prev, crossover, crossunder, ...) and `draw.*` handles are created
  once in `createState`, inside the guarded creation window.
- Main thread. An L2 frame costs about 0.2 ms at p99; lane columns are
  megabytes and are handed out by reference. Never copy them per bar.

another indicator's bespoke series, hover tooltips for a new indicator,
alerts or notifications (no alert system exists in the web app at all).

Cycle-1 definition of an "alert": a documented condition rendered as a marker
and surfaced in the indicator's own table or legend. A notification channel is
a separate SDK project, not something a specialist builds inside an indicator.

## 5. Settings and presets

Field kinds: boolean, checkboxList, radioGroup, select, numeric, color,

appear in the schema (a test enforces it) and presets come for free. Since

history, so a setting that changes which bars are colored or marked must be

## Rules that are not negotiable

- Read buy/sell through `barSides` (`apps/web/src/lib/indicators/barSides.ts`).
  Never compute sell as `volume - buy_volume`. A bar `barSides` reports as not
  `known` draws no delta (`null`), not zero.
- `missing` is not `empty`. Unavailable data yields `null`; a quiet bar with
  complete data yields the real value (which may be 0).
- Tick-based indicators read `ctx.ticks` (declare `ticksWanted: true`) and must
  check `ticks.coverageOf(bar.ts_open, bar.ts_open + bar.interval_ms)`:
  `"all"` is complete, `"thin"` means only large prints are present, `"none"`
  means nothing. Anything that counts or sizes trades is valid only on `"all"`.
  `ctx.trades` with `tradeAvailability === "LIVE_COMPLETE"` is the per-bar
  alternative when you only need the forming bar's prints.
- Order-book indicators read `ctx.l2`. Output `null` unless
  `l2.availability === "LIVE"`, `l2.trusted()` is true and the channel you read

# Data for indicator authors

[Handbook](../../README.md) · [Indicator index](README.md) ·
[Onboarding](../../operations/00-developer-onboarding.md) ·
[Indicator SDK](../indicator-sdk/TA.01-indicator-authoring-core-evidence.md)

An indicator never opens SQLite, S3 or a provider connection itself. It reads
what the runtime and the archive deliver through a small number of supported
boundaries. This page names those boundaries, says what each one carries for
each instrument, and lists the rules every indicator has to follow. The code
named here is the authority; when this page and the code disagree, the code
wins and this page is the defect.

## Three sources of data

| Source | How it reaches an indicator | You need | When it is missing |
|---|---|---|---|
| **Live ticks** | Terminal C holds the provider session and sends canonical frames (`bar`, `trade`, `book`, `health`, profiles, VPIN readings) over the local `/ws` WebSocket | Binance: nothing. dxFeed: layer 2 (Tailscale broker) | dxFeed instruments show *History only*: with layer 1 their recorded host history still loads, without new ticks |
| **Warm-up** | Before live ticks arrive, the runtime reads recent history through its storage reader: candles, large trades, aggressive prints, volume profile, VPIN calibration | Layer 1 (WireGuard + bearer); otherwise only a local collector's SQLite | The indicator starts from live ticks only and reports itself not ready |
| **Archive** | Historical Mode reads candles through `/archive/query` and asks the host for four studies through `/archive/study` | Layer 1 | Historical Mode shows *Historical Mode needs host data access* |

The three layers are explained in [onboarding](../../operations/00-developer-onboarding.md);
`npm run doctor` reports which ones a machine has.

Warm-up and live ticks meet in the runtime; the archive is a separate path used
only by Historical Mode. A successful warm-up does not prove an archive
partition exists, and an archive answer says nothing about the live collector
today.

Live Mode also has a bounded `band_history` request for a historical price band.
The laptop sends the instrument, price range and time window through Terminal C;
the host replays its recorded raw depth and returns resting size and traded
flow per row. Institutional Order Blocks v1 reads a block the visible live
history did not cover from the host's stored heatmap columns first
(`/heatmap/columns`, cut to the block's rows in the browser) and uses
`band_history` only when the host has no stored columns for the pair or that
read fails. Session Levels reads a touched level's five minutes and a range's
totals from the same stored columns, with no raw-replay fallback. A missing book interval remains a gap, never a
zero-liquidity observation. Each host read is capped at two hours, 256 rows and
100,000 row/column cells; the client pieces longer requests. This is an
on-demand derivation, **not a stored canonical L2 row dataset**, and it does
not make order-book indicators available in the separate Historical Mode
archive. See the [wire contract](../../contracts/ws-frame-contract/v1/ws-frame-contract-v1.md)
and `apps/runtime/src/server/band-history.js` for the exact boundary.

## What each instrument has

| Instrument | Live ticks | Warm-up from the host | Historical candles | Historical studies |
|---|---|---|---|---|
| BTC, ETH spot and perpetual (Binance) | always | yes | 1m, 1h, 1d, each with taker buy volume | none yet |
| ES, NQ (continuous futures) | with layer 2 | yes, what the weekday collector captured | 1m, 1h, 1d | profile, VPIN, large prints, bar flow |
| AAPL, TSLA (equities) | with layer 2 | yes, what the weekday collector captured | 1m, 1h, 1d | profile, VPIN, large prints, bar flow |
| NVDA (equity) | with layer 2 | yes, what the weekday collector captured | not archived | none |

**Equity candles are regular session only**, live and historical alike:
09:30–16:00 New York time, with the exchange's holidays and early closes from
[`config/market-calendar.json`](../../../config/market-calendar.json). Hourly
bars start at 09:30, the last one ends at the bell, and a daily bar is that
session. Pre-market and after-hours prints are not in equity candles. Futures
and crypto candles are UTC-aligned and cover every traded minute.

Other timeframes are resampled in the browser from those rungs. The governed
instrument list, exact provider symbols and tick sizes live in
[`config/market-instruments.json`](../../../config/market-instruments.json);
the archive's list lives in `apps/web/src/lib/archive/historicalCatalog.ts`.

The four studies are computed on the host from trade-derived families, so the
browser never pages minute rows. Their request, limits and refusals are in the
[archive study contract](../../contracts/archive-study/v1/archive-study-v1.md).
In short: a profile per requested range, VPIN over whole UTC weeks (at most 26),
and large prints and bar flow over one bar-aligned range of at most 5,000 bars.

## Which indicators work in Historical Mode

`HISTORICAL_INDICATOR_POLICIES` in `apps/web/src/lib/chart/indicatorRegistry.ts`
decides this, per indicator, from the capabilities the selected archive
provides. There are three policies:

| Policy | Needs | Works on |
|---|---|---|
| Candles | `ohlcv` | every archived instrument |
| Candle flow | `ohlcv` + `buy_volume` | Binance (candles carry taker buy volume) and ES/NQ/AAPL/TSLA (the `bar_flow` study supplies both sides) |
| Trade families | `ohlcv` + `trade_families` | ES/NQ/AAPL/TSLA |

An indicator can also be marked unavailable with a reason, as order-book and
every-trade indicators are: the archive has no historical depth and keeps only
the largest prints of each minute.

## Rules every indicator follows

**Read buy and sell through `barSides`.** Never compute sell volume as
`volume - buy_volume`. `apps/web/src/lib/indicators/barSides.ts` returns
`{known, buy, sell, unknown, delta, sided}` for a bar. It uses an explicit
`sell_volume` when the bar has one, and falls back to `volume - buy_volume`
only for bars that carry just a buy side. That fallback is exact for Binance,
where every trade has a taker side. It is not exact for equities.

**Unsided volume is real and large for equities.** A Databento equity trade
often has no aggressor side. Measured on the host (Report 54): ES and NQ are
effectively fully sided, but AAPL is about 40% unsided on one-minute bars and
65–75% on hourly and daily bars; TSLA is 35–55%. Historical bars carry that
volume separately as `unknown`, and `unsidedShare(bars)` gives the share to
show beside an equity delta. Counting it as selling would make every equity
delta read bearish by that amount.

Live dxFeed bars built from the tape carry buy and sell only when every trade in
that minute had a side. A minute with any unsided trade carries neither, so
`barSides` reports it unknown and it draws no delta, which is common for
equities. Stored native dxFeed candles carry both sides explicitly (volume at
the ask and at the bid), with any remainder unknown.

**`missing` is not `empty`.** A study reports ranges it could not read as
`missing`; draw them as unavailable, never as zero. It reports ranges it read
and found no trades in (a weekend, an overnight hour for an equity) as `empty`,
and those legitimately have nothing to draw. A bar with no trades is absent
from `bar_flow`; draw no delta for it, not a zero delta.

**Gate on capabilities, not on provider names.** Declare what the indicator
needs through its `HISTORICAL_INDICATOR_POLICIES` entry. Do not branch on
`provider === "BINANCE"`. The map is typed over every indicator id, so a new
indicator does not compile until it has a policy.

**Warm-up failure is not an empty signal.** When the storage reader cannot
reach the host it reports the read as unavailable. Show the indicator as
warming up or degraded, never as a flat or zero reading.

**Quantities are provider units.** Futures sizes are contracts, equity sizes
are shares, Binance sizes are the base asset. Do not add them across providers
or convert them to a notional the provider did not report.

**Need a new trade-derived aggregate?** Do not fetch minute rows into the
browser. A new study is a change to the archive study contract and the host,
and goes through the owner.

## Adding an indicator that works in both modes

1. Create `apps/web/src/lib/indicators/<name>/`. The folder owns the whole
   indicator: computation, geometry, primitive and settings. Follow the
   [SDK execution model](../indicator-sdk/TA.01-indicator-authoring-core-evidence.md).
   Its settings dialog gets [setting presets](setting-presets.md): a
   `settingsSchema` is enough for the generic dialog, and a hand-built one
   declares a preset schema for every setting it stores.
   Keep at most three primary controls on the Inputs tab and give every other
   input `tab: "advanced"`, which the generic dialog renders as a collapsed
   Advanced group.
2. Register it in `INDICATOR_REGISTRY` and give it a
   `HISTORICAL_INDICATOR_POLICIES` entry that names what it needs.
3. Read sides through `barSides`. For example, a cumulative delta that leaves
   bars without a known side undrawn:

   ```ts
   import type { BarFrame } from "../../../types/frames";
   import { barSides } from "../barSides";

   export function cumulativeDelta(bars: readonly BarFrame[]): (number | null)[] {
     let total = 0;
     return bars.map((bar) => {
       const sides = barSides(bar);
       if (!sides.known) return null;
       total += sides.delta;
       return total;
     });
   }
   ```

4. Check it in Live Mode on Binance (every machine can), then in Historical
   Mode on BTC and on one futures and one equity instrument (layer 1). On AAPL,
   confirm the unsided share is shown and the delta is not skewed.
5. Add tests for the computation, lifecycle, capability gating and rendering,
   as listed under *Adding or changing an indicator* in the
   [indicator index](README.md).

Ok only closes. The generic body (`GenericIndicatorSettingsBody`) stacks
fields vertically, label above control; sliders show the value inline
(`Inner band (σ) 1.00`); tabs **Inputs** / **Visibility** appear only when a
field declares `tab`. Hand-built dialogs (Aggressive Orders, the heatmap)
copy the same tab strip and classes. Every dialog has presets for free from
its schema (`docs/architecture/indicators/setting-presets.md`).

### 1.4 Copy tone

Sentence case labels with the unit in brackets: `Session length`,
`Lookback (bars)`, `Show orders larger than (BTC)`. Hints are plain full
sentences that say what the control does and what it costs:
"Changing the anchor, the session length or a band width replays every bar."
Legend details and status strings are short lowercase phrases after ` · `.
Status chips: `LIVE`, `SYNCING`, `STALE`, `QUIET`, `HISTORY ONLY`,
`Feed unavailable`, `Live profile catching up`, `VPIN waiting for trades`,
`Analytics incomplete — reload to rebuild`. Numbers are mono and tabular.

### 1.5 How indicators signal warm-up, degraded and unavailable today

- An SDK indicator returns `null` from `readOutput` until it has enough bars:
  the line simply starts later (RSI draws nothing for its first 14 bars).
  Nothing tells the trader it is warming up.
- Hand-wired indicators put state in the legend detail (`Warming ·`,
  `Unavailable ·`, `history unavailable`, `waiting for the book`) or in a
  status chip. The data rule is "warm-up failure is not an empty signal";
  never draw a zero or a flat line for data you do not have
  (`data-for-indicator-authors.md`, Rules).
- A throw, a non-finite number or a non-string colour latches a fault: the
  indicator goes blank until removed and re-added, with no message in the
  legend. Fail closed to `null` instead.
- Historical Mode greys out indicators whose policy says unavailable and
  shows the `unavailableReason` sentence.

## 2. The standard every new indicator follows

### 2.1 Default view: readable in three seconds

1. One question, one primary mark. The first thing on screen is the series,
   band or marker that answers the indicator's question. Secondary context
   (a baseline, a threshold) is thinner and lighter.
2. At most two lines and one fill at default settings. A third series goes
   behind a Visibility toggle, off by default.
3. Pane or overlay: a value in price units (a level, a band, a VWAP) is an
   `overlay`. A bounded ratio, score or oscillator is an `ownPane` with
   `priceLines` at its decision levels and a fixed `autoscaleRange`, so the
   pane does not rescale as the trader scrolls. Do not share a pane unless
   the two indicators are read together.
4. Line widths: primary 2, secondary 1. Fills between 0.12 and 0.25 alpha.
5. It must read on both charts: the cream live chart and the dark Historical
   chart. Take a screenshot of each before handing over (section 4).
6. The registry `label` carries the default parameter, as `RSI (14)` does,
   so the legend explains itself.

### 2.2 Controls: at most three primary, the rest Advanced

- Inputs tab: at most three controls without a `tab` (or `tab: "inputs"`).
  These are the ones a trader changes in the first session: the length,
  the threshold, the mode.
- Everything else that changes the calculation: `tab: "advanced"`. The
  generic dialog renders it as a closed **Advanced** group at the end of the
  Inputs tab (prototype on the UX branch, see
  `PM/cycle1/advanced-settings-proposal.md`; until merged, keep the list of
  advanced keys in the README and leave them off the schema's first screen).
- Colours, show/hide toggles, opacity, labels: `tab: "visibility"`.
- Prefer `slider` or `select` with named stops over free `numeric` boxes;
  a numeric field needs `step > 0` or the generic dialog refuses every value.
- One explanatory paragraph at most on the Inputs tab; a one-line hint per
  control is fine. The full explanation lives in the indicator's README.
- Use the generic dialog. A hand-built dialog needs a PM decision.
- Settings that depend on the instrument (a size floor) use
  `settingsFieldsFor` for the suggested value, never a provider branch in
  the schema.

### 2.3 Colour semantics

- Green/red (`--bull`/`--bear`, or the candle-up/down colours on the dark
  chart) only for direction or side: buying vs selling, above vs below.
- A non-directional series takes one neutral colour from the house set:
  purple `#4d3d78` / `#8672b3`, blue `#2563eb`, amber `#facc15` (dark chart
  only). Never introduce a new hue for a single indicator.
- Thresholds and reference lines: `rgba(10,10,10,0.3)` on the cream chart,
  `rgba(250,250,247,0.32)` on the dark one.
- Warning or "degraded" state: `--warn`, never red (red means sell).
- Expose a colour in Visibility only when the trader could plausibly need
  to change it; the default must already be right.

### 2.4 Markers

- At most two event types per indicator, one shape each: `arrowUp` below the
  bar and `arrowDown` above it for directional events, `circle` for neutral.
- `text` at most three characters; prefer none.
- Density: at default settings on a 1m BTC chart, no more than about one
  marker per ten bars on average. If the fixture shows more, raise the
  default threshold; the trader can lower it under Advanced.
- Marker colour equals the colour of the line or side it belongs to.
- Markers never replace the line: a marker says "here", the series says "why".

### 2.5 "Alert conditions" without an alert system

There is no notification channel. An alert condition is:

1. a named, documented condition in the README under **Alert conditions**
   (name, exact rule, which bar it fires on, how often it fires on the
   fixture);
2. a marker on the bar where it fires (section 2.4);
3. a row in the indicator's own `draw.table` (top-right): condition name,
   the bar time and the value, for example `Squeeze fired · 12:34 · 1.8σ`.
   A generic SDK indicator cannot write to the legend detail today, so the
   table is the place.

Never promise a notification in copy. Use the condition's name
("Squeeze fired"), not the word "alert", in anything the trader reads.

### 2.6 First use: before warm-up completes

- Draw nothing for bars without a value (`null`), never a zero or a flat
  line, never a partial window as if it were full.
- While warming up, the table shows one row: `Warming up · 37 of 200 bars`.
  When data the indicator needs is not there (ticks in replay, L2 before
  the first frame, a timeframe outside the gate), the row says what it needs
  in the trader's terms: `Needs live trades`, `Needs 1m to 15m`,
  `Waiting for the book`. Remove the row once the indicator is live.
- State the warm-up length in the README and keep it under the chart's
  retention (`maxReplayBars`, at most 10,080 1m bars).
- Replay honesty: a value the replay cannot compute (tick-only inputs) is
  `null`, and the README says that history looks different from live.

### 2.7 Tooltips and hover: what can and cannot be promised

Only hand-wired indicators have hover today: `fvgDelta` and `sessionLevels`
through `getHoverData` in `ChartPanel.tsx`, and the Aggressive Orders bubbles
and the heatmap through their own primitives. A new SDK indicator gets no
tooltip without a chart-pipeline change and PM approval. Therefore:

- Design so nothing essential needs a hover: an SDK line has no price-axis
  value label, so the current value and the state go in the table, and
  thresholds are drawn as `priceLines` (which do get axis labels).
- You may implement `getHoverData` for later wiring, but the README must not
  claim a tooltip, and the screenshots must not show one.

### 2.8 Copy for labels and hints

- Labels: sentence case, at most four words, unit in brackets:
  `Lookback (bars)`, `Minimum size (BTC)`.
- Hints: one or two sentences, present tense, say what changes and whether
  it replays ("Replays every bar").
- Use the feed vocabulary from `CAPABILITIES.md`: top of book, aggregated
  depth, tape, candles. Say "estimate" when it is one; never "detects" or
  "predicts" unless validation established it.
- Legend detail and table cells: at most 30 characters, ` · ` between parts,
  numbers tabular.
- Status phrases are lowercase and concrete: `waiting for the book`, not
  `Initializing…`.

# Validation protocol (cycle 1)

Owner: validation and performance specialist. Applies to every indicator that
reaches step 6 of the pipeline in `PM/CHARTER.md`. The harness that runs these
checks lives on the repository at `apps/web/src/lib/chart/validation/`
(import from `./validation/index.ts`); each utility has its own proving test in
`apps/web/src/lib/chart/validation/tests/`. A check is not passed because the
specialist says so; it is passed because a vitest file in the indicator's
`tests/` folder (or a validation spec next to it) runs the check and the
evidence file named in the report records the result.

Vocabulary: **replay** is the runtime's `onSnapshot`/activation pass over the
retained bars (`replaying: true`, no `trades`, `HISTORICAL_UNAVAILABLE`);
**live** is bars arriving one at a time through `onBar` as `APPENDED`, then
`REPLACED_EDGE` for every forming revision, then `REPLACED_EDGE` once more when
the bar closes. The harness classifies arrivals with the chart's own
`mergeChartBar`, so a duplicated closed bar is a `REPLACED_EDGE` and a late bar
is a `REBUILT`, exactly as `ChartPanel` would dispatch them.

## The checks

Each check states the method, the pass criterion and how the evidence is
recorded. "Evidence file" means a vitest file committed on the indicator's
branch whose test names match the check, plus any JSON or log the test writes
(kept under `PM/log/validation/<indicator>/`).

### 1. No future data

Method. `checkTruncationInvariance(def, bars, settings)` replays the fixture
once in full, then once truncated at every index (`sampledIndices` for series
longer than 1,000 bars: every 25th index plus the last 50), and compares the
committed outputs of every line and every marker at or before the cut. Run it
on at least `compressionBreakoutBars()` and `trendBars()`; tick and book
indicators also run it with the fixture's `extras` (`ticks` from `tapeOf`, `l2`
from `fakeL2` with `atTime` cutting walls and events at the bar close).

Pass. `report.ok === true`: zero output disagreements at tolerance 0 (a
documented floating-point tolerance is acceptable only for a value computed in
a different order live versus replay, never for a different value), zero marker
disagreements, no fault. An indicator that reads `barIndex`/`barCount` to place
anything is suspect by default and must show this check passing.

Evidence. Test named `no future data: truncation invariance` in the
indicator's tests; `summarizeTruncation(report)` written to the log on failure.

### 2. Replay versus live equivalence

Method. `checkLiveReplayEquivalence(def, bars, settings, { revisionsPerBar: 5 })`
feeds every bar as five forming revisions (`closed: false`, path open through
the wicks to the close, volume growing with buy, sell and unknown volume scaled
independently through `barSides`, so an equity bar's unsided share stays
unsided) followed by the closed bar,
through the real runtime, and compares the committed outputs and markers with a
clean replay of the same bars. For a tick or book indicator supply `tradesFor`
and `extras` so the live side sees what the terminal would give it.

Pass. Either `report.equal === true`, or the indicator's doc page states the
exact difference and the test pins it: for a tick-only indicator the expected
and accepted difference is `outputsEqual === true`, replay markers `[]`, live
markers present (`largeTradeBubbles` is the reference: see
`validation/tests/liveEquivalence.test.ts`). Any output difference on a
candle-only indicator fails; it means forming revisions were committed (the
harness catches this with a running sum that ignores `replace`).

Evidence. Test named `replay versus live equivalence`; the documented
difference quoted in the indicator's doc page under "Replay and Historical
Mode".

### 3. Gap, duplicate and late-event behavior

Method, five parts, all through the live driver so the runtime's own
classification is what the indicator sees:

- Duplicate closed dispatch: `checkDuplicateClosedIdempotent(def, bars, settings, index)`.
  The duplicate must be classified `REPLACED_EDGE` and the result must equal a
  feed in which the bar arrived once.
- `REBUILT`: `checkRebuiltEquivalence(def, bars, settings, lateIndex)`. A bar
  arriving two bars late must leave the indicator equal to a clean replay
  (`sawRebuilt === true`). Module-level state (a cache keyed by instrument, a
  slot pool) is where this fails; the runtime replays, the module does not.
- Reconnect that clears the tick store: an arrival script whose `act` hook
  resets the `AggressiveTape` and hands a new `IndicatorTicks` to the session
  (`session.setTicks`). Every bar whose window the store no longer covers must
  read `null`, never a stale value (reference: `tickVolume` in the same test file).
- Out-of-order prints: `tapeOf` with prints in shuffled order must give the
  same per-window sums as in-order arrival (`syntheticTape.test.ts`); an
  indicator that keeps its own print buffer must show the same.
- Time gap: run the indicator on `timeGapBars()`; the output at
  `labels.firstBarAfterGapIndex` must follow the indicator's documented gap rule
  (restart, carry, or null), and nothing before the gap may change.
- Book indicators: run the same checks with `extras.l2` from `fakeL2`. Its
  `trusted(ts)` is false before the segment start, on a GAP or null segment and
  when `l2_walls` or `l2_events` is unsynced; `events(cursor)` is `complete`
  only for an exact cursor on a synced ring past any reported loss, exactly as
  `EventRing.since`; so an indicator's missing-event and untrusted gates can be
  exercised with `patch({ synced: { l2_events: false } })`, `missedEvents`, a
  cursor before `eventResetSeq`, or `segment: segmentOf(start)`.

Pass. All five hold; no fault; no `NaN`.

Evidence. Tests named `duplicate closed bar is idempotent`, `late bar rebuilds
to the replay`, `reconnect clears the store honestly`, `out-of-order prints`,
`time gap`.

### 4. Warm-up

Method. Replay a fixture shorter than the warm-up length and one exactly at
it; read every line of `replayCapture(...).outputs`.

Pass. Every value before the documented warm-up length is `null`; the first
non-null value appears exactly at the documented index; no value anywhere is
`NaN`, `Infinity`, or a fabricated `0` standing in for "not yet" (a genuine
zero from complete data is fine, and the test must say which it is). The
warm-up length (bars, and for tick indicators the coverage condition) is stated
in the doc page and in a `staticHint` of the settings schema.

Evidence. Test named `warm-up is null, never NaN or zero`; the doc sentence.

### 5. Marker and alert budget

Method. `countMarkers(def, bars, settings, { live })` on a busy synthetic
instrument: `trendBars({ count: 1000 })` or the breakout fixture with
`busyTapeFor(bars, { printsPerBar: 60 })` supplying trades live (whales at 0.2
percent of prints, 100 times the small size). In cycle 1 an alert is a marker
(`PM/CHARTER.md`), so this is also the alert budget. Record `per1000Bars`,
`maxPerBar`, `barsWithMarkers` and the breakdown by shape and color.

The budget carries `faulted`; a run in which the runtime latched the indicator
counts nothing and `judgeBudget` fails it whatever the rate.

Pass. Ceilings, unless the build brief sets a different one with a reason:
at most **40 markers per 1,000 bars** for a signal-type tool (a trader can act
on roughly one mark an hour on 1-minute bars), at most **200 per 1,000** for a
descriptive annotation tool (levels, labels), and at most **3 markers on one
bar**. A duplicated closed bar must not add markers (`countMarkersOver` with
`duplicateClosedArrivals`). The judged verdict is `judgeBudget(budget, ceiling,
maxPerBar).ok`.

Evidence. Test named `marker budget`; `summarizeBudget(...)` line in the log.

### 6. Performance

Method. The three probes in `perfProbe.ts`, run with `NODE_OPTIONS=--expose-gc`:

- `probeReplay(def, bars10080, settings)`: activation over 10,080 one-minute
  bars (the chart's retention cap); per-`onBar` p50 and p99, wall time of the
  whole replay, heap delta.
- `probeFormingBar(def, warmup, settings, { seconds: 60, revisionsPerSecond: 50, printsPerMinute: 1000 })`:
  one bar revised 3,000 times with 1,000 prints landing in a real tape
  (`ctx.ticks`) and in `ctx.trades` (`LIVE_COMPLETE`); per-revision p50 and p99.
- `probeRollover(def, bars10080, settings, { extraBars: 1000 })`: the chart at
  the cap, then 1,000 more bars so the front rolls off and `discardLeading`
  runs; retained output lengths, markers older than the oldest retained bar,
  heap growth per extra bar. The appended bars are built by `rolloverBar`,
  which writes sides through `barSides` (sided, buy-only and unsided bars each
  stay what they were).
- `probeReplayPooled(def, bars, settings, { warmupRuns: 3, timedRuns: 5 })`:
  the method frozen in the Relative Volume brief (amendment 9): three untimed
  warm-up replays, five timed replays, per-bar samples pooled, p99 by nearest
  rank, timed region `onBar` plus `readOutput` with no-op draw and marker
  namespaces, no runtime bookkeeping. Its `extras` go through the same
  knowledge-time cutoffs as `indicatorRuntime.makeCtx`: `liquidity.atTime(barClose)`
  with a null answer meaning unavailable, and `l2.atTime(barClose)` with a
  fallback to the uncut view. When a brief states a per-bar p99
  criterion (Relative Volume: under 0.05 ms over the first 10,080 bars of the
  crypto fixture) this is the probe that judges it; `probeReplay` remains the
  measurement of a real activation and keeps the reference rows below.

Pass. Replay p99 ≤ 0.5 ms and total replay wall ≤ 2 s for a candle indicator
(≤ 5 s for a book or tick indicator that reads the store per bar); forming
revision p99 ≤ 1 ms (an indicator revised 50 times a second gets at most 50 ms
of the main thread per second); after the rollover every output line has
exactly 10,080 entries, `markersBeforeRetention === 0`, and heap growth is
flat: `bytesPerExtraBar` within 3× the harness floor measured below (about
370 B per bar, which is the runtime's own output arrays and the bar frames
themselves). A probe that reports `faulted` fails regardless of timing.

Evidence. JSON written by the indicator's baseline test
(`VALIDATION_BASELINES_OUT`), kept under `PM/log/validation/<indicator>/perf.json`,
and the three formatted lines in the report.

Reference points measured on this container (4 cores, Intel Xeon 2.10 GHz,

### 7. Baseline comparison

For the cycle-1 indicator the brief freezes the fixtures and the acceptance
numbers: `relativeVolumeEquityFixture()` (labels `anomalyIndices`,
`predictableSlotIndices`, `evaluationIndices`, `sessionStarts`) and its
`{ flatSeasonality: true }` control, judged by the recall and false-positive
bounds in `PM/cycle1/brief-rvol-clock.md`; the fixture's own proving test is
`validation/tests/relativeVolumeFixtures.test.ts`. The general rule follows.

Method. The build brief names the simpler baseline (a rolling average, plain
RVOL, a raw imbalance line, a candle-only version of the same idea). The
specialist implements the baseline as a `RuntimeIndicatorDef` in the
indicator's `tests/` (or Codex does, gate G4) and runs both on labelled
fixtures:

- Descriptive tools are judged on **detection accuracy on labelled fixtures**:
  for `compressionBreakoutBars` the detection index versus
  `labels.breakoutIndex` (hit if within the documented tolerance, early if
  before, late if after, plus false positives inside `compressionStart..breakoutIndex`);
  for `volumeSpikeBars` the same against `labels.spikeIndex`; for
  `rangeBars` and `trendBars` the false-positive count. Run each fixture over at
  least 10 seeds and report hits, early, late and false positives for the tool
  and the baseline side by side.
- L1 tools must pass the **whale-versus-crowd** fixture: `whaleVersusCrowd()`
  builds two tapes making the identical candle (print count withheld); the tool
  must respond differently to the two tapes while the candle-only baseline, by
  construction, cannot. `largeTradeBubbles` is the reference (one bubble on the
  whale tape, none on the crowd tape, `syntheticTape.test.ts`).
- L2 tools state what is **observed** (ladder, walls, events as served) versus
  **inferred**, and the baseline comparison is run on the same `fakeL2` script so
  the book is the same for both.

Pass. The report states, in one sentence, what the tool shows that the baseline
hides, and the table shows it: strictly fewer false positives at equal or
better hits, or hits the baseline cannot produce (whale versus crowd). A tool
that only matches the baseline is returned to the backlog.

Evidence. Test named `beats the baseline on labelled fixtures`; the
side-by-side table in the report.

### 8. Predictive claims

Method. Any claim of the form "after X, price tends to Y" is predictive. The
specialist freezes the rule (parameters included) on a development period,
then measures it on an **unseen period** chosen after the rule was frozen:
a different seed range of the synthetic fixtures (declared in the test before
the development runs are made), and, where this container can reach it, a live
Binance stretch recorded after the rule was written. Forward observation only:
the outcome window starts at the signal bar's close and uses no bar before it.

Overfitting rule. Choosing the best of several parameter sets, thresholds or
variants by their result on the development period and reporting that result
is rejected. At most **one** rule is carried to the unseen period; if it fails
there the claim is dropped, not re-tuned. Every variant tried is listed in the
report with its development result so the selection is visible.

Pass. The unseen-period result is reported with its sample size and with the
same statistic on the baseline; a claim with fewer than 30 signals in the
unseen period is reported as "insufficient evidence", not as a pass. Marketing
copy may state only what the unseen period supports.

Evidence. `PM/EXPERIMENTS.md` entry with the frozen rule, the declared unseen
period, every variant, and the two results.

### 9. Equity unsided volume

Method. Run the indicator on `equityUnsidedBars()` (dxFeed equity identity;
every third bar carries no side, the others carry both sides and a 40 percent
unsided remainder) and read every output that depends on sides.

Pass. On `labels.unsidedIndices` every side-dependent output is `null`
(`barSides(bar).known === false` draws nothing, never zero). On
`labels.partiallySidedIndices` the delta equals `buy - sell` from `barSides`
and the unsided remainder is **not** counted as selling; where the tool shows a
delta on equities it shows `unsidedShare` beside it or in the doc. The code
reads sides only through `barSides`: `grep -n "volume - " <folder>` and
`grep -n "buy_volume" <folder>` outside `barSides` calls must be empty. No gate
on `provider === "..."` except to label units.

Evidence. Test named `equity unsided volume is honest`.

### 10. Historical Mode policy honesty

Method. Read the indicator's `HISTORICAL_INDICATOR_POLICIES` entry and the data
it actually reads in `onBar`:

| Reads | Required policy |
|---|---|
| candles only (`bar` OHLCV) | `OHLCV_POLICY` |
| `barSides` / `buy_volume` | `CANDLE_FLOW_POLICY` |
| `ctx.ticks`, `ctx.trades` | `unavailableReason` (or `l2_prints` only if the doc proves the verified hours suffice) |
| `ctx.l2`, `ctx.liquidity`, `bandHistory` | `l2_states` / `l2_walls` capabilities or `unavailableReason` |
| host studies | `TRADE_FAMILY_POLICY` |

Then replay the indicator with `replayCapture` and no extras (what a candle
archive gives): a tick or book indicator must produce `null` outputs and no
markers (`largeTradeBubbles` and the `tickVolume` reference pass this); a
candle-flow indicator on bars without `buy_volume` must produce `null`.

Pass. The policy row matches the table; the replay-without-extras result is
honest nulls; the doc page's "Historical Mode" paragraph says the same thing as
the policy; `historicalIndicatorAvailability(id, capabilities)` for the
instrument's real capability set agrees with the doc's claim of where the tool
works. A policy that promises Historical Mode for data the archive does not
contain fails the indicator outright.

Evidence. Test named `Historical Mode policy is honest` (asserting the policy
entry and the null replay).

# UX standard for new indicators (cycle 1)

Written by the UX seat from the code in `Terminal-L1-L2-development-indicator-sdk`
(snapshot 2026-10-26) and from rendered charts (`PM/cycle1/screenshots/`).
Code wins over this page; report a disagreement to the PM. The rules in
part 2 are what every new indicator must follow; part 1 is what the house
already does, so a new indicator looks like it belongs.

## 1. House conventions observed

### 1.1 Colours

| Where | Value | Source |

| Dark chart (Historical Mode, `.shell.historical-active`) | background `#111316`, up `#36d684`, down `#f16a72`, text `#9ca3af` | `DARK_CHART_PALETTE`, `App.css` |

The candles are monochrome on the default chart, so green and red are free
for meaning: buyers, sellers, bull, bear. Hand-wired lines use
`INDICATOR_LINE_WIDTH = 2`; an SDK line takes `lines[].lineWidth` and falls
back to 2. SDK line series are created with `lastValueVisible: false` and
`priceLineVisible: false`, so an SDK line has no current-value label on the
price axis; own-pane `priceLines` do get dotted 1 px lines with axis labels
(`ChartPanel.tsx`, runtime series creation).

### 1.2 Legend rows

Top-left stack over the chart, one white pill per indicator
(`IndicatorLegendRow`): mono 11 px bold label, an optional grey `detail`, and
eye / gear / trash buttons that appear on hover or focus. In Historical Mode
the pill is dark. The label is the registry `label` (`"RSI (14)"`, so the
default parameter is in the name). The detail is set per indicator by hand
in `MainPanel.tsx`; a generic SDK indicator with a `settingsSchema` gets label
and gear only. Observed detail strings: `Swing 20`, `≥ 5 ct`,
`Bar volume × typical price`, `Live only · 20 bars required`,
`Warming · ≥ 0.50z`, ` · history unavailable`, `waiting for the book`,
`reconnecting`, `loading the view's prints`.

### 1.3 Settings dialog

`IndicatorSettingsModal` is a draggable fixed panel about 320 px wide, title
bar with the indicator label and a close button, body, footer with
**Reset to default**, **Defaults ▾** (presets) and **Ok**. Edits apply live;
Ok only closes. The generic body (`GenericIndicatorSettingsBody`) stacks
fields vertically, label above control; sliders show the value inline
(`Inner band (σ) 1.00`); tabs **Inputs** / **Visibility** appear only when a
field declares `tab`. Hand-built dialogs (Aggressive Orders, the heatmap)
copy the same tab strip and classes. Every dialog has presets for free from
its schema (`docs/architecture/indicators/setting-presets.md`).

### 1.4 Copy tone

Sentence case labels with the unit in brackets: `Session length`,
`Lookback (bars)`, `Show orders larger than (BTC)`. Hints are plain full
sentences that say what the control does and what it costs:
"Changing the anchor, the session length or a band width replays every bar."
Legend details and status strings are short lowercase phrases after ` · `.
Status chips: `LIVE`, `SYNCING`, `STALE`, `QUIET`, `HISTORY ONLY`,
`Feed unavailable`, `Live profile catching up`, `VPIN waiting for trades`,
`Analytics incomplete — reload to rebuild`. Numbers are mono and tabular.

### 1.5 How indicators signal warm-up, degraded and unavailable today

- An SDK indicator returns `null` from `readOutput` until it has enough bars:
  the line simply starts later (RSI draws nothing for its first 14 bars).
  Nothing tells the trader it is warming up.
- Hand-wired indicators put state in the legend detail (`Warming ·`,
  `Unavailable ·`, `history unavailable`, `waiting for the book`) or in a
  status chip. The data rule is "warm-up failure is not an empty signal";
  never draw a zero or a flat line for data you do not have
  (`data-for-indicator-authors.md`, Rules).
- A throw, a non-finite number or a non-string colour latches a fault: the
  indicator goes blank until removed and re-added, with no message in the
  legend. Fail closed to `null` instead.
- Historical Mode greys out indicators whose policy says unavailable and
  shows the `unavailableReason` sentence.

## 2. The standard every new indicator follows

### 2.1 Default view: readable in three seconds

1. One question, one primary mark. The first thing on screen is the series,
   band or marker that answers the indicator's question. Secondary context
   (a baseline, a threshold) is thinner and lighter.
2. At most two lines and one fill at default settings. A third series goes
   behind a Visibility toggle, off by default.
3. Pane or overlay: a value in price units (a level, a band, a VWAP) is an
   `overlay`. A bounded ratio, score or oscillator is an `ownPane` with
   `priceLines` at its decision levels and a fixed `autoscaleRange`, so the
   pane does not rescale as the trader scrolls. Do not share a pane unless
   the two indicators are read together.
4. Line widths: primary 2, secondary 1. Fills between 0.12 and 0.25 alpha.
5. It must read on both charts: the cream live chart and the dark Historical
   chart. Take a screenshot of each before handing over (section 4).
6. The registry `label` carries the default parameter, as `RSI (14)` does,
   so the legend explains itself.

### 2.2 Controls: at most three primary, the rest Advanced

- Inputs tab: at most three controls without a `tab` (or `tab: "inputs"`).
  These are the ones a trader changes in the first session: the length,
  the threshold, the mode.
- Everything else that changes the calculation: `tab: "advanced"`. The
  generic dialog renders it as a closed **Advanced** group at the end of the
  Inputs tab (prototype on the UX branch, see
  `PM/cycle1/advanced-settings-proposal.md`; until merged, keep the list of
  advanced keys in the README and leave them off the schema's first screen).
- Colours, show/hide toggles, opacity, labels: `tab: "visibility"`.
- Prefer `slider` or `select` with named stops over free `numeric` boxes;
  a numeric field needs `step > 0` or the generic dialog refuses every value.
- One explanatory paragraph at most on the Inputs tab; a one-line hint per
  control is fine. The full explanation lives in the indicator's README.
- Use the generic dialog. A hand-built dialog needs a PM decision.
- Settings that depend on the instrument (a size floor) use
  `settingsFieldsFor` for the suggested value, never a provider branch in
  the schema.

### 2.3 Colour semantics

- Green/red (`--bull`/`--bear`, or the candle-up/down colours on the dark
  chart) only for direction or side: buying vs selling, above vs below.
- A non-directional series takes one neutral colour from the house set:
  purple `#4d3d78` / `#8672b3`, blue `#2563eb`, amber `#facc15` (dark chart
  only). Never introduce a new hue for a single indicator.
- Thresholds and reference lines: `rgba(10,10,10,0.3)` on the cream chart,
  `rgba(250,250,247,0.32)` on the dark one.
- Warning or "degraded" state: `--warn`, never red (red means sell).
- Expose a colour in Visibility only when the trader could plausibly need
  to change it; the default must already be right.

### 2.4 Markers

- At most two event types per indicator, one shape each: `arrowUp` below the
  bar and `arrowDown` above it for directional events, `circle` for neutral.
- `text` at most three characters; prefer none.
- Density: at default settings on a 1m BTC chart, no more than about one
  marker per ten bars on average. If the fixture shows more, raise the
  default threshold; the trader can lower it under Advanced.
- Marker colour equals the colour of the line or side it belongs to.
- Markers never replace the line: a marker says "here", the series says "why".

### 2.5 "Alert conditions" without an alert system

There is no notification channel. An alert condition is:

1. a named, documented condition in the README under **Alert conditions**
   (name, exact rule, which bar it fires on, how often it fires on the
   fixture);
2. a marker on the bar where it fires (section 2.4);
3. a row in the indicator's own `draw.table` (top-right): condition name,
   the bar time and the value, for example `Squeeze fired · 12:34 · 1.8σ`.
   A generic SDK indicator cannot write to the legend detail today, so the
   table is the place.

Never promise a notification in copy. Use the condition's name
("Squeeze fired"), not the word "alert", in anything the trader reads.

### 2.6 First use: before warm-up completes

- Draw nothing for bars without a value (`null`), never a zero or a flat
  line, never a partial window as if it were full.
- While warming up, the table shows one row: `Warming up · 37 of 200 bars`.
  When data the indicator needs is not there (ticks in replay, L2 before
  the first frame, a timeframe outside the gate), the row says what it needs
  in the trader's terms: `Needs live trades`, `Needs 1m to 15m`,
  `Waiting for the book`. Remove the row once the indicator is live.
- State the warm-up length in the README and keep it under the chart's
  retention (`maxReplayBars`, at most 10,080 1m bars).
- Replay honesty: a value the replay cannot compute (tick-only inputs) is
  `null`, and the README says that history looks different from live.

### 2.7 Tooltips and hover: what can and cannot be promised

Only hand-wired indicators have hover today: `fvgDelta` and `sessionLevels`
through `getHoverData` in `ChartPanel.tsx`, and the Aggressive Orders bubbles
and the heatmap through their own primitives. A new SDK indicator gets no
tooltip without a chart-pipeline change and PM approval. Therefore:

- Design so nothing essential needs a hover: an SDK line has no price-axis
  value label, so the current value and the state go in the table, and
  thresholds are drawn as `priceLines` (which do get axis labels).
- You may implement `getHoverData` for later wiring, but the README must not
  claim a tooltip, and the screenshots must not show one.

### 2.8 Copy for labels and hints

- Labels: sentence case, at most four words, unit in brackets:
  `Lookback (bars)`, `Minimum size (BTC)`.
- Hints: one or two sentences, present tense, say what changes and whether
  it replays ("Replays every bar").
- Use the feed vocabulary from `CAPABILITIES.md`: top of book, aggregated
  depth, tape, candles. Say "estimate" when it is one; never "detects" or
  "predicts" unless validation established it.
- Legend detail and table cells: at most 30 characters, ` · ` between parts,
  numbers tabular.
- Status phrases are lowercase and concrete: `waiting for the book`, not
  `Initializing…`.

export function usableVolume(volume: unknown): number | null {
  return typeof volume === "number" && Number.isFinite(volume) && volume >= 0 ? volume : null;
}

export interface Observation {
  tsOpen: number;
  volume: number;
}

export interface ObservationRing {
  readonly capacity: number;
  /** Oldest first; never longer than `capacity`. */
  readonly items: Observation[];
  /** What the newest insertion pushed out, kept until that tail is superseded so a correction can restore it. */
  evictedByTail: Observation | null;
}

export function createRing(capacity: number): ObservationRing {
  const size = Number.isFinite(capacity) ? Math.max(1, Math.floor(capacity)) : 1;
  return { capacity: size, items: [], evictedByTail: null };
}

export function ringInsert(ring: ObservationRing, observation: Observation): void {
  ring.items.push(observation);
  if (ring.items.length > ring.capacity) ring.evictedByTail = ring.items.shift() ?? null;
}

/** Changes the volume of the observation filed under `tsOpen` in place; false when none is filed. */
export function ringUpdate(ring: ObservationRing, tsOpen: number, volume: number): boolean {
  for (let index = ring.items.length - 1; index >= 0; index -= 1) {
    if (ring.items[index].tsOpen === tsOpen) {
      ring.items[index].volume = volume;
      return true;
    }
  }
  return false;
}

/** Removes the observation filed under `tsOpen` and restores what its insertion evicted. */
export function ringRemove(ring: ObservationRing, tsOpen: number): boolean {
  for (let index = ring.items.length - 1; index >= 0; index -= 1) {
    if (ring.items[index].tsOpen !== tsOpen) continue;
    ring.items.splice(index, 1);
    if (ring.evictedByTail !== null) {
      ring.items.unshift(ring.evictedByTail);
      ring.evictedByTail = null;
    }
    return true;
  }
  return false;
}

/** The tail that inserted into this ring has been superseded by a newer bar: its eviction is final. */
export function ringSupersede(ring: ObservationRing): void {
  ring.evictedByTail = null;
}

/** Median of the ring's volumes (mean of the two middle values for an even count); null when empty. */
export function ringMedian(ring: ObservationRing, scratch: number[] = []): number | null {
  const count = ring.items.length;
  if (count === 0) return null;
  scratch.length = count;
  for (let index = 0; index < count; index += 1) {
    // Insertion sort: the ring holds at most 60 values and this runs once per bar.
    const value = ring.items[index].volume;
    let position = index;
    while (position > 0 && scratch[position - 1] > value) {
      scratch[position] = scratch[position - 1];
      position -= 1;
    }
    scratch[position] = value;
  }
  const middle = count >> 1;
  const median = count % 2 === 1 ? scratch[middle] : (scratch[middle - 1] + scratch[middle]) / 2;
  return Number.isFinite(median) ? median : null;
}

export function ringMean(ring: ObservationRing): number | null {
  const count = ring.items.length;
  if (count === 0) return null;
  let sum = 0;
  for (let index = 0; index < count; index += 1) sum += ring.items[index].volume;
  const mean = sum / count;
  return Number.isFinite(mean) ? mean : null;
}
