# Binance Backpressure Queue

> **Historical implementation evidence.** This dated page records the result
> of a completed build or audit. It is not a current deployment/health
> statement; use the handbook and final-state overview for supported operation.

The connection has two explicit pressure boundaries. The collector first uses
a bounded per-route raw-frame FIFO before JSON parsing. After normalization,
a per-`(symbol, eventType, interval)` FIFO handles `TRADE`, `BOOK_TICKER`, and
`KLINE`; `DEPTH` remains on its ordered book-reconciliation path. Both stages
use moving-head queues, bounded time slices, and observable pending,
high-water, overflow, and drain counters.

## Profiles

- Browser-facing relay: 500 events per tuple, up to 50 deliveries per turn, `DROP_OLDEST`. This bounds display latency where current state is more useful than an unbounded stale display backlog.
- Durable collector raw ingress: 50,000 frames and 64 MiB per route, up to 1,000 frames or 8 ms per turn, `FAIL`. The WebSocket transport pauses at 40% of the frame bound or 50% of the byte bound and resumes after draining below 10% and 12.5%, respectively. This applies TCP receive backpressure before application memory reaches its hard limit.
- Durable collector normalized ingress: 50,000 events per tuple, up to 1,000 deliveries or 8 ms per turn, `FAIL`. `FAIL` is deliberately not `DROP_OLDEST`: an incoming frame or event that cannot be accepted is explicitly accounted for and terminates the strict capture session instead of allowing a partially complete run to continue as valid.

Every drop or overflow emits telemetry with an exact affected count. The collector persists this evidence. An `event_dropped` or strict-policy queue overflow is terminal and makes the session `INVALID`; the terminal policy prevents a known-incomplete raw capture from being presented as research-complete.

## Delivery safety

Raw-frame drains are isolated by physical route. Normalized drains allocate
work fairly among non-empty subscribed tuples and rotate which tuple is served
first. Both check elapsed monotonic time every eight items and yield once the
time budget is exhausted, so a burst cannot monopolize the event loop merely
because the item-count budget has not been reached. Immediately before
normalized dequeue and delivery the connection verifies that the collector
session is still active and the tuple remains subscribed, then verifies the
dequeued tuple generation before dispatch. An unexpected route disconnect
does not erase frames or events already accepted into the durable collector
queues; an explicit terminal disconnect does. A listener that unsubscribes
and resubscribes during the same batch therefore cannot receive stale-generation events.

Transport pause/resume is hysteretic, per route, and observable through active-pause, pause-duration, pause/resume-count, and failure metrics. A deliberately paused route is not misclassified as provider silence while accepted frames remain queued. If the transport cannot slow a burst and either hard bound is reached, the existing exact-loss telemetry and terminal `INVALID` policy still apply.

`stale` and `recoveryState` are recomputed at delivery rather than frozen at enqueue. Removing one consumer from a shared tuple preserves the remaining consumers; removing the final consumer performs the provider unsubscribe and clears only that tuple.

The queue uses a moving head and occasional compaction rather than repeated array shifts, avoiding quadratic copying under bursts. Drain scheduling is deduplicated so overlapping turns cannot stack.

Collector startup registers all tuples through `subscribeMany()`. New tuples are grouped by physical route, so the six SPOT streams use one provider control message instead of violating Binance's five-inbound-messages-per-second connection limit. A batch is validated before mutation, rolls back desired state on send failure, and initializes recovery only after every route group is accepted for sending.

## Files

- `apps/runtime/src/providers/binance/binance-backpressure-queue.js` - FIFO, limits, policies, counters, and fair drain
- `apps/runtime/src/providers/binance/binance-connection.js` - raw ingress, route/generation checks, and production profile integration
- `apps/runtime/scripts/collect/run-collector.js` - source of the durable-collector profile numbers above (50,000/64 MiB raw ingress, 50,000/tuple normalized, both `FAIL`)
- `apps/runtime/src/storage/collector-feed-maintenance.js` - `listCollectorSubscriptions()`, source of the six-SPOT-streams startup batch (TRADE + KLINE + DEPTH × 2 symbols; no `BOOK_TICKER` in the collector's own subscription set)

## Deliberately separate concerns

Outbound Binance control-message rate limiting and REST retry policy are independent from consumer-delivery backpressure. No priority queue is used: all active tuple keys receive an equal fair share.
