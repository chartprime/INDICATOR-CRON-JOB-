# VWAP Bands (P4.15)

> **Historical implementation evidence.** This dated page records the result
> of a completed build. It is not a current deployment/health statement; use
> the [final-state indicator index](README.md) and the handbook for supported
> operation.

VWAP Bands is an **overlay reference line** in the `l1` category: the
volume-weighted average price of the volume traded since the current session
opened, with volume-weighted deviation bands, priced by **this terminal's own
L1 print store** and by nothing else.

It is registered as `vwapBands` (`kind: "runtime"`, category `l1`), with the
line keys `vwap`, `upper1`, `lower1`, `upper2` and `lower2` on the price pane.

It is deliberately a second indicator rather than a second setting on
[Session VWAP](P4.14-session-vwap-evidence.md): that one is priced by the bar
and works in every mode, this one is priced by the tape and says so. The two
share their session kernel and can be on at the same time.

The one thing it will not do is price a bar from its candle. A candle does not
say where inside itself the volume traded, so a bar drawn that way is an
estimate with no prints behind it — the exact claim this indicator exists to
avoid making. A bar the store does not cover therefore adds **nothing**, and
what the line shows is the volume-weighted average of the prints the terminal
actually holds.

## The source: `AggressiveTape`, never the order book

`ctx.ticks` is the store the whale detector and Aggressive Order Flow already
read (`apps/web/src/lib/indicators/aggressive-orders/aggressiveTape.ts`), handed
to the indicator runtime through `apps/web/src/lib/chart/indicatorTicks.ts`. It
holds:

- **every print of the live pair from the moment it lands** — one
  `AggressivePrint` per trade, with its own price and size, capped at
  `MAX_TAPE_PRINTS` (250 000) and trimmed from the oldest end; and
- **the history the server could serve for the stretch before this browser
  connected**, which is a bounded pool kept **above a size floor**.

So both the average and σ come out exact to the print, not to a price bucket
and not to a candle — where the store covers the window.

### The readings of coverage are told apart, not blurred

`IndicatorTicks.coverageOf(fromTs, toTs)` answers with one of three readings, and
`sumPrintsIn` then sums the prints in the half-open window `[fromTs, toTs)`:

| Reading | Meaning | What a bar contributes |
| --- | --- | --- |
| `"prints"` | The window is covered end to end: a live stretch (the current one, whose end may still be forming, or one before a reconnect, up to its last live print) past the newest live print the store's size cap dropped, or history the server served above a floor of zero. | The window's prints — including none at all, which is a real answer for a window inside the live stretch. |
| `"thin"` | Only floor-filtered history covers the window, or a live stretch the store's 250k-print cap has since dropped prints from, so prints are missing. | The window's prints — used, and named, because the alternative is no tick data at all for that stretch. The average leans towards the larger prints. |
| `"none"` | Nothing covers the window. | Nothing. |

A covered window's answer is final: it does not fall through to another source
for volume of its own. Neither an uncovered window nor a covered one that printed
nothing creates a hole in the line — the session keeps its running average,
exactly as the shared kernel already treats a bar of zero volume, so the average
carries flat across them rather than being invented or restarted.

There is no fourth option hiding behind those three: no endpoint in this system
serves "every trade between two timestamps" for a past range (`TA.03.5`), so a
bar older than the store cannot be made tick-true, and this indicator would
rather draw nothing for it than draw something that is not a print. What the
line is made of is stated in the settings hint and kept in state
(`VwapBandsSource`).

Which reading drew a bar is **not coloured apart on the chart**: a per-bar colour
cannot survive a cosmetic recolour (`recolor` is handed a stored string and no
bar), so such a marking would silently flatten on the first colour change. That
is the same constraint that keeps Session VWAP's two invisible colours apart.

## The two VWAPs are told apart by colour

Both indicators can be on the chart at once, and they answer different questions,
so they do not share a palette:

| Line | Session VWAP | VWAP Bands |
| --- | --- | --- |
| `vwap` | `#3b82f6` (blue) | `#8b5cf6` (violet) |
| `upper1` / `lower1` | the same blue at 100 % | `#e879f9` (fuchsia) at 100 % |
| `upper2` / `lower2` | the same blue at 80 % | the same fuchsia at 80 % |

The **opacity ladder is shared** (`sessionVwapBandColor`, 100 % then 80 %), so both
indicators read the same way: the solid line is the average and the faint ones are
its deviations, the outer band faintest. VWAP Bands additionally gives its bands a
hue of their own, because it is the indicator whose bands are meant to be looked
at — the deviations are the reason to read a print-priced VWAP at all.

The ladder is applied when the colour is painted, not stored: the colour pickers
are plain `<input type="color">` fields, which hold `#rrggbb` and cannot carry an
alpha, and a recolour then re-derives both bands from whatever hue was chosen
instead of keeping a stale fade. The average itself is never faded.

## The session kernel is imported, not copied

Everything about sessions comes from
`apps/web/src/lib/indicators/session-vwap/sessionVwap.ts`: the UTC-aligned
windows and the session-length list (so a VWAP segment lines up with the Session
Delta Profile zone drawn beside it for the same length), the running sums and
band maths, the eight-session accumulator bound, and the session-join rule —
the bar walking up to a session's end is painted transparent, because
lightweight-charts strokes a segment with the colour of the point it *starts*
from. Copying any of it would have meant two answers to the same questions.

A `REPLACED_EDGE` re-delivers the developing bar with its updated numbers, so the
bar's earlier contribution is subtracted before the new one is measured. Since
the store is read live, a print that landed since the last delivery is picked up
by the next one with no notification path of its own.

## Two anchors: the session, or a window anchored N bars back

The **Anchor** dropdown chooses what the average is measured over, and the input
belonging to the other anchor is hidden rather than left inert. Both VWAPs offer
it and mean the same thing by it: the options, the bounds, the settings fields and
the rule that finds the anchor live in the shared session kernel, not here.

| Anchor | Window | Its own input |
| --- | --- | --- |
| Session VWAP | the current session window, the same UTC-aligned windows Session VWAP draws | Session length |
| Lookback VWAP | the bars from N bars back from the newest bar up to it, 300 by default | Lookback (bars), a slider from 10 to 500 |

The lookback window needs no session concept at all. It is **a bar, not a period**:
the anchor is the `lookbackBars`-th bar back from the newest bar of the series
being fed, which only the series itself can say, so the runtime hands the
indicator its position in that series (`ctx.barIndex` / `ctx.barCount`) and the
anchor is decided on the replay that establishes the window. It then **stays put**
while bars arrive and the window develops from there to the newest bar — the same
shape as a session window developing from its own first bar, with a bar count in
place of a period. This is anchored, not rolling: nothing falls out of the window
as it grows. [Session VWAP](P4.14-session-vwap-evidence.md) offers the same
dropdown and the same behaviour, differing only in what prices each bar.

Both anchors accumulate into the same three running sums (`addVwapSample` /
`removeVwapSample`, shared with the session path), which is why the band maths, the
sigma ladder, the palette and the two band colours are the same for both instead
of being written twice.

Three consequences are deliberate:

- **Nothing is drawn before the anchor.** Those bars are outside the window even
when the store can price them, and the line begins on the anchor bar.
- **A bar inside the window that the store cannot price adds nothing**, so the
average carries flat across it, exactly as a session does with a bar of zero
volume.
- **Nothing is painted transparent in lookback mode.** The join rule exists to
stop two *sessions* being read as one line; an anchored window has no boundaries
to join.

If the chart holds fewer bars than the lookback, there is no bar N back to anchor
on, so the window starts on the first bar it is given.

The anchor and the lookback are both `recompute` settings, so switching either one
replays the bars and rebuilds the window, exactly as a session-length change does
for the other anchor. A reload or a recompute therefore re-anchors: the anchor is
N bars back from the newest bar *at that moment*.

## Handover: why the runtime has a `ticksWanted` flag

`AggressiveTape` is created per live pair and mutated in place, so the runtime
cannot be notified per print — and does not need to be. What it does need is to
hear about the **store being handed over**, because that is what backfills the
bars that were drawn before it existed:

- `IndicatorRuntime.setTicks(ticks, bars)` swaps the pointer on every active
  record and replays **only** the indicators that declared `ticksWanted: true`.
  For everyone else it is a pointer swap with no replay.
- Handing over the same store twice (which happens on every tape-identity
  refresh) is a no-op, so nothing thrashes.
- History is the one thing that lands for bars already drawn: the server's
  prints and their coverage arrive after the store was handed over. The tape's
  `historyVersion` moves for those and never for a live print, and `ChartPanel`
  subscribes to the tape: when it moves, it waits 250 ms for the reply to settle
  and calls `IndicatorRuntime.refreshTicks(bars)`, which replays the same
  `ticksWanted` indicators (PR #29 review).
- `ChartPanel` exposes it as `applyTicks(tape)`, a channel separate from
  `applyAggressiveTape(tape)`. MainPanel withholds the tape from the **bubbles**
  above the aggressive timeframes and while Aggressive Orders is off the chart,
  but hands the store itself over whenever it exists: the timeframe a cluster is
  measured in says nothing about whether a print happened, and hiding one
  indicator must not take the prints away from another that prices volume by
  them.
- The **deep history pool** is still requested by Aggressive Orders itself
  (`requestAggressiveHistory`), so a user who wants prints older than the live
  stretch on the chart needs that indicator enabled too. The store still gets
  the snapshot's own trades on connect either way.
- With **no store at all** — Historical Mode, or a pair whose feed is not up —
  every bar adds nothing, so the indicator draws nothing rather than falling back
  to candles. That is the deliberate consequence of having no fallback, and it is
  why Historical Mode answers "unavailable" instead.

## Limits

- **Historical Mode is not offered**, because a replay carries no trades and
  there is no candle fallback to draw from instead: the registry policy for
  `vwapBands` states that reason rather than leaving an empty line the user
  cannot explain.- **The tape's reach is the store's reach.** Live prints are exact from connect;
  older bars are only as good as the floor-filtered history that was fetched, and
  bars beyond it have no value at all.
- **A lookback window longer than that reach is full of bars that price
  nothing**, so its average is really the average of the priced bars inside it.
  The window still starts exactly `lookbackBars` back, so the number on the slider
  keeps meaning what it says.
- **The line begins where the tape begins.** A session that opened before the
  store did draws nothing until the first covered bar, rather than projecting an
  average backwards over volume it never saw.
- **A bar longer than the session** cannot resolve a boundary, so no join is
  hidden in that case rather than blanking the line.
- σ collapses onto the VWAP when the window's prints all share one price.

## Settings

| Setting | Tab | Effect |
| --- | --- | --- |
| Anchor | Inputs | Recompute. Switches between the session window and the rolling lookback, replaying the bars to rebuild whichever accumulator it needs. |
| Session length | Inputs | Recompute. Replays every bar, rebuilding each session from the store. Hidden while the lookback anchor is selected. |
| Lookback (bars) | Inputs | Recompute. Re-anchors the window and rebuilds it from the store. Slider, 10–500 bars, default 300. Hidden while the session anchor is selected. |
| Inner / outer band (σ) | Inputs | Recompute. Resizes the whole distribution, so it replays the bars. |
| Show deviation bands | Visibility | Cosmetic. Paints the band series transparent rather than deleting it. |
| VWAP / band colors | Visibility | Cosmetic. Recolored in place; a hidden session join stays hidden. The bands are painted at the shared ladder's opacity whatever hue they hold. |

Every line carries a `recolor`, so a purely cosmetic edit takes the cheap
recolor path instead of a full replay. As with Session VWAP there is deliberately
no "sessions shown" setting: the numeric line channel cannot retract points it
has already emitted, so the retained-session bound is fixed.
