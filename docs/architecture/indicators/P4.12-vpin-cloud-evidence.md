# VPIN Cloud (P4.12)

> **Historical implementation evidence.** This dated page records the result
> of a completed build or audit. It is not a current deployment/health
> statement; use the handbook and final-state overview for supported operation.

VPIN Cloud is a **signal indicator**, not a computation-and-visualization
tool like Volume Profile/Delta Profile. It measures informed-trading-flow
toxicity (volume-synchronized VPIN) from real trade-exact, true-aggressor
data on both providers, and renders as an active/inactive cloud gated by
hysteresis — it carries a real gate and a direction, not a neutral
histogram.

## Methodology

1. **Volume-clock calibration** — `v_bucket` sized off the instrument's
   own recent median daily traded volume (`bucketsPerDay=360`).
2. **Trade-exact bucket sealing** — running buy/sell total per instrument;
   crossing `v_bucket` seals a bucket. A single oversized print can cross the
   threshold by an arbitrary multiple, and its remainder is **carried into the
   next bucket**, sealing as many buckets as it fills. Volume is conserved: no
   part of a print is discarded.
3. **W-bucket rolling mean** of imbalance → signed VPIN (`w=20`).
4. **Self-calibrating Z-score** against the instrument's own recent
   signed-VPIN history (`nBaseline=100`, needs 50 sealed buckets before
   any Z-score computes — set below the standard 5,000/2,500 baseline
   deliberately, since this terminal's own collected trade history isn't
   deep enough yet for a larger window to ever produce a reading;
   revisit once more history accumulates).
5. **Hysteresis** (Schmitt trigger, `zOn=1.0`/`zOff=0.2`) — a same-
   direction reading that drops below `zOn` but stays above `zOff`
   remains active.
6. **Velocity/acceleration** — not a separate readout; drives the cloud's
   own motion (bloom-in, acceleration-edge brightening, tapered decay).

## Backfill

Cold-start backfill runs a SQL-side aggregate query (`readSlicedNotional`)
against a covering index — `(symbol, market_kind, ts, side, price, size)`
for Binance, `(symbol, asset_class, event_time, event_kind, valid_tick,
aggressor_side, price, size)` for dxFeed — collapsing raw trades into
250ms time slices in one indexed pass, then feeding the unchanged engine
two synthetic buy/sell notional entries per slice instead of walking
every trade individually in JS. An adapter without `readSlicedNotional`
falls back to per-trade replay automatically. Runs inside a
`worker_threads.Worker`, off the main event loop, for all three servers.

**Accepted approximation:** collapsing a slice's trades into at most two
synthetic ingest calls can, in a sufficiently dense sub-slice volume burst, seal
a bucket at a different point than true per-trade replay would have. The
*ordering* within a 250 ms slice is what is approximated — total volume is
still conserved, exactly as it is for a single oversized print.

## Why the live tick and the backfill both run in workers

A live VPIN tick is deliberately a **short-lived, read-only job on a worker
thread**. `better-sqlite3`'s synchronous API is safe inside a worker but is not
acceptable on the WebSocket relay's event loop: a slow historical cursor page
would delay book, tape, health and client pings for every connected client.
Cold-start backfill runs in a worker for the same reason at larger scale.

Worker input is **structured-cloned**, so the worker builds a fresh session and
then replaces its state with the cloned `vpinState` it was handed. That
preserves the baseline and hysteresis history exactly — which is the whole
point, since a reset baseline would silently restart the Z-score calibration —
while keeping the database adapter local to the worker thread.

The backfill page ceiling (`DEFAULT_MAX_BACKFILL_PAGES`) is set deliberately
high because **the worker deadline, not the page count, is the real guard**. A
low page cap would silently truncate an active BTC perpetual backfill and
present the result as complete; the wall-clock deadline instead lets the state
report itself as unavailable, which is the truthful outcome.

## Bucket sealing and the overflow remainder

VPIN is defined in **equal-volume time**, so a single print finishes one bucket
and continues into the next. The remainder is carried, never discarded:
throwing it away would make the next bucket's contents depend on how the
exchange happened to fragment a print rather than on flow, and would lose real
volume.

Measured against the shipped engine: one 350-notional print against a
`vBucket` of 100 seals **three** buckets and leaves **50** in the accumulator.

## Idle rendering

The motion layer runs on a 100 ms clock. It must not re-map every retained bar
and rebuild polygons while VPIN is inactive, so an inactive motion state short-
circuits before `mapReadingsToBars`. New readings and new bars still request
their own redraw — this only removes idle animation work from the chart path.

## Reading-to-bar mapping and staleness

Readings are volume-sealed; bars are time-ruled. A reading therefore has to
carry forward across bars until the next one seals — `mapReadingsToBars`
paints each bar with the latest reading sealed as of that bar's close.

That carry is **bounded**. The cloud stops once a bar's close is more than
`STALENESS_CADENCE_MULTIPLE` (4) times the median observed interval between
readings past the reading's own `seal_ts`. The bound is derived from the
readings themselves rather than fixed in wall-clock time, because sealing is
volume-driven: a four-minute cadence on a busy instrument and a forty-minute
cadence on a quiet one are both normal, and a fixed bound would either cut off
the quiet instrument or fail to protect the busy one. Median, not mean, because
seal intervals are spike-prone.

An **inactive** reading already ends the cloud. The bound covers the case
inactivity does not: readings stopping altogether — a dropped feed, a failed
warm-up, an instrument that goes quiet — where the last *active* reading would
otherwise paint a toxicity signal over every later bar indefinitely. With
fewer than two readings there is no cadence to infer and no bound is applied.

## Visual design

Four-layer gradient polygon per active reading (100/70/42/18% height,
0.10/0.19/0.32/0.52 opacity), anchored away from price (buy cloud below
bar low, sell cloud above bar high), gap-aware run-splitting, only one
side ever active at a time. Motion layer: bloom-in pulse on activation,
acceleration-driven outer-edge brightening while a move is still building
(static once plateaued), tapered decay on deactivation (hysteresis itself
stays binary; only the rendered fade is tapered) — all driven by real
engine state (`z_vpin_velocity`/`z_vpin_acceleration`/`activated_at_ts`),
not a cosmetic loop independent of it.

## Configuration

One user-facing sensitivity dial, not raw Z-score parameters. Default
derived from that instrument's own backfilled activation history (85th
percentile of `|z_vpin|`), falling back to a fixed default when fewer
than 20 valid readings exist yet. Sensitivity changes re-run hysteresis
client-side against the raw `z_vpin` stream, no server round-trip.

## Provider provenance

Both providers compute VPIN trade-exact, live. dxFeed's `UNDEFINED`-
aggressor trades are excluded outright — a null-side trade is a complete
no-op to the bucket sealer, never touching the accumulator or `openTs`.

## Verification obligations

Bucket-sealing correctness against hand-built trade sequences, including
the whale-trade overflow-discard case; hysteresis holding a same-
direction reading between `zOff` and `zOn`; the sliced-backfill fast path
matching full per-trade replay when no slice's volume approaches
`vBucket`, and diverging in the documented way when it does; the
adapter-capability fallback path; only one cloud side ever active per
reading; the motion layer surviving a burst that seals multiple inactive
buckets within one decay window, and surviving pan/zoom during a decay
window. Full backend and frontend suites green; zero comments in
production code.

Live verification: confirmed rendering on BTCUSDT SPOT, real active/
inactive transitions. dxFeed live verification is still outstanding.
