# Drawing-Tool Infrastructure + Trendline (P4.04)

> **Historical implementation evidence.** This dated page records the result
> of a completed build or audit. It is not a current deployment/health
> statement; use the handbook and final-state overview for supported operation.

`lightweight-charts` v5.2.0 ships no drawing-tool API (confirmed against the
installed package's own typings — no `DrawingPrimitive`/`LineTool` anywhere).
P4.04 builds that capability from scratch: a click-to-place pointer-event
state machine, a symbol/market-scoped persistence layer, and a canvas
primitive — proven with Trendline as the first real tool. Fibonacci (P4.05),
Measure (P4.06), and Anchored VWAP (P4.07) add only their own geometry and
render logic on top of this; none of them need their own pointer-event
plumbing or persistence design.

## Files

- `apps/web/src/lib/chart/drawingStore.ts` — persistence: validation, per-instrument
  scoping, the per-instrument cap
- `apps/web/src/lib/indicators/drawing-tools/trendlineGeometry.ts` — pure pixel projection, hit-testing,
  and the placement state machine (`advanceDrawingPlacement`)
- `apps/web/src/lib/indicators/drawing-tools/trendlinePrimitive.ts` — the `ISeriesPrimitive` that
  renders committed lines, the selection highlight, and the live pending
  preview line
- `apps/web/src/components/chrome/DrawingToolbar.tsx` — the Cursor/Trendline mode
  selector
- `apps/web/src/components/chart/ChartPanel.tsx` — the pointer-event wiring
  (`subscribeClick`/`subscribeCrosshairMove`/`keydown`), primitive
  attach/detach, per-instrument reload on symbol switch
- `apps/web/src/components/chart/MainPanel.tsx` — active-tool state, toolbar
  render, `instrumentIdentity` passthrough into `ChartPanel`

## Interaction model

Click-to-place, not drag-to-place: a first click sets the first endpoint, the
cursor previews a live dashed line via the existing `subscribeCrosshairMove`
hook (already used for the whale-marker tooltip), and a second click commits.
The tool stays active after a commit so multiple trendlines can be placed
without reselecting it from the toolbar. With no tool active, a click instead
hit-tests existing trendlines for select/deselect; `Delete`/`Backspace`
removes a selected one (endpoint drag-to-reposition is explicitly deferred,
not part of this ticket's scope).

All of this state lives in a pure reducer, `advanceDrawingPlacement`, kept
independent of the real chart object specifically so it's unit-testable —
this codebase has no `lightweight-charts` mock and `ChartPanel.tsx` carries
no component-level tests today (a known, already-documented gap). Every
transition (setting a tool, both clicks of a placement, an invalid/off-scale
click, Escape at each state, delete with and without a selection) is tested
directly against the reducer, the same mitigation already used for
`appendedBarIsContiguous`.

**A genuine interaction conflict, not just new code**: two rapid placement
clicks are indistinguishable from a native browser double-click. The existing
`dblclick`-triggered zoom reset is now gated on no drawing tool being active,
otherwise placing a trendline quickly would also reset the chart's zoom
mid-placement.

Clicks and the live preview are ignored outside the main price pane
(`paneIndex !== 0`) — Trendline, like the other three Day-6 tools, is a
price-pane-only tool; CVD's separate pane is out of scope here, unlike Delta
Divergence's deliberate dual-pane design.

## Persistence

One `localStorage` key (`terminal.drawings.v1`) holding every drawing across
all instruments; each entry is self-scoping via its own `FrameIdentity` +
`symbol` fields, reusing `parseFrameIdentity` from `types/frames.ts` rather
than re-implementing identity validation. Scoping is by full identity, not
symbol alone — `BTC-USDT` spot and `BTC-USDT` perpetual are different
instruments with different price ranges, the same reasoning `identitiesMatch`
already encodes elsewhere in this codebase. Loading validates every field
per-item (a malformed entry is dropped individually, not the whole list) and
truncates any single instrument's entries past `MAX_DRAWINGS_PER_INSTRUMENT`
(200) — a defensive backstop against tampered `localStorage`, not just
normal-path enforcement (normal adds are already capped before they're ever
written).

## Proving the infrastructure actually generalizes

The ticket's own acceptance criteria required demonstrating this with a real
throwaway spike, not asserting it. A second `type: "fibonacci_SPIKE"` variant
was temporarily added to `DrawingToolId`/`DrawnObject`, proven to round-trip
through the exact same persistence path and commit through the exact same
placement reducer with zero reducer changes, then removed before this ticket
closed.

One genuine, useful finding came out of it: once `DrawnObject` becomes a real
union (P4.05 onward), the two `ChartPanel.tsx` call sites that hand a filtered
drawing list to `TrendlinePrimitive.setDrawings` will need a one-line
`.filter(d => d.type === "trendline")` — `TrendlinePrimitive` only ever
renders trendlines, so a generic `DrawnObject[]` needs narrowing before it
reaches a type-specific renderer. This is expected, narrow, and exactly the
"add your own render logic" work P4.05 is scoped for — not evidence of a
plumbing gap.

## Closure audit findings

A fresh, adversarial re-read after P4.05 landed (both tools now exist to
audit together) found one real, serious bug in this ticket's own code: the
effect that reloads drawings on a symbol switch unconditionally reset
`drawingPlacementRef.current` to `DRAWING_PLACEMENT_IDLE` without touching
`activeDrawingToolRef.current`. If a tool was active when the user switched
symbols, that left the two refs inconsistent — the toolbar still showed
the tool selected, but the placement reducer was in `"idle"`, and
`advanceDrawingPlacement`'s `click` handling treats an idle-state click with
no hit as an absorbing no-op. Every click on the new symbol would silently
do nothing until the user manually reselected the tool. Fixed by routing the
reset through `advanceDrawingPlacement`'s own `setTool` event with the
*current* active tool, which already correctly derives `"placing"` (tool
active) vs `"idle"` (no tool) — the same derivation `setActiveDrawingTool`
itself already used, now applied consistently everywhere
`drawingPlacementRef` is touched. A dedicated reducer test now pins down the
exact contract this fix depends on (re-applying `setTool` mid-placement
cancels the pending point but stays placeable, not idle) — mutation-tested
by temporarily breaking the reducer and confirming the test fails.

The same pass also hardened `advanceDrawingPlacement` itself: it used to
handle its fourth event type (`deleteSelected`) by elimination — the final
branch had no `event.type` check at all, relying on it being the only
variant left after the three explicit `if` blocks above it. Converted to an
exhaustive `switch`, mutation-tested by adding a 5th event variant with no
case and confirming `tsc` now fails to compile rather than silently
mishandling it. This matters concretely for P4.06/P4.07, which will very
likely need their own new event types (drag-based for Measure, single-click
for Anchored VWAP).
