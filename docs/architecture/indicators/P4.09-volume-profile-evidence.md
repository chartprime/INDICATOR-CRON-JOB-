# Volume Profile (P4.09)

> **Historical implementation evidence.** This dated page records the result
> of a completed build or audit. It is not a current deployment/health
> statement; use the handbook and final-state overview for supported operation.

Volume Profile is a **computation-and-visualization tool**. It shows how
traded volume distributed across price over a period, from real L1 trade
prints on both providers, not a candle-range approximation. It carries no
score, gate, or trading signal.

> **Changed 2026-10-03 — one indicator, three views.** Volume Profile, Net
> Delta Profile and Delta Profile are one registered indicator now,
> `sessionVolumeProfile` / "Session Volume Profile (Volume / Net Delta /
> Delta)", with a **View** dropdown that selects `volumeProfile`,
> `netDeltaProfile` or `deltaProfile`. One
> server `ProfileFrame` feeds all three, exactly as before; what changed is
> that the three registrations, the two bespoke settings modals and the three
> per-view visibility paths collapsed into one, and the palette became one
> shared set of fields (defaults are this indicator's own old colours, so the
> volume view is unchanged by default). Do not describe them as three
> indicators elsewhere; the separate-registration sections below are kept as
> the historical record of how this got here.

Net Delta Profile (see [Net Delta Profile](#net-delta-profile)) renders the
same server profile frames as signed net-delta bars. It is the
`netDeltaProfile` view of that one indicator; the id and every saved
preference survive through `sessionProfileSettings.ts`'s migration.

The migration (run once by `loadHistoricalIndicatorPreferences`, which is
handed the matching favourites key) counts any trace of the three legacy ids:
saved settings, a recorded visibility, or a listing in favourites, since most
workspaces only toggled them. The view is the legacy profile that was on the
chart and showing (saved settings, then a delta view, break ties); a delta
view keeps the colours it had, its own saved palette over its own shipped
defaults; the merged profile is hidden only if every legacy profile that was
on the chart was hidden.

## Product contract

Three modes, selected in the settings modal:

1. **Continuous** — a recurring period (5m to 1 week) that resets on its own
   clock boundary, one chain of adjacent profile blocks.
2. **Per-Candle** — one profile per chart candle, aligned to the candle's own
   open/close.
3. **Fixed Range** — a one-off, user-anchored window, placed with the Drawing
   Tools "Fixed Range" tool (two-click placement, like Trendline/Fibonacci),
   not a mode switch in the settings modal.

Additional controls: a bin-size multiplier (2 by default), and the indicator's
own visibility toggle.

**Historical rendering is always on, no separate toggle.** Whenever the
indicator is enabled and visible, every epoch-aligned period currently in
the chart's visible range renders as its own shaded zone — the live/
developing period on the right edge, closed periods to its left — the same
"historical plus live together" behaviour every other marker-based
indicator in this terminal already has. This applies to both Continuous
and Per-Candle; a manually drawn Fixed Range zone renders alongside them.

## Methodology

- **Row width.** Always a whole number of ticks, snapped to a multiple of the
  rollup cache's own grain so a historical zone's bucketing lines up exactly
  with a fresh server-side computation over the same window. The width is
  _derived_, never typed in directly:
  - **Automatically (default).** From the instrument's own **volatility (ATR)**:
    the reading is projected onto the session's span with the random-walk
    `sqrt(sessionMs / barIntervalMs)` scaling, then divided by a row-count
    target (75) to give a bin size. Both the live period and its closed
    neighbours size from the same fixed reference window, which is what lets
    them share one grid.
  - **By the bin-size multiplier.** The _"Bin size"_ field scales that derived
    width. `2` is the default, **higher is coarser bins** (wider rows, fewer of
    them) and **lower is finer** (narrower rows, more of them). It is a float,
    and the accepted range is `0.02`–`10`. It is strictly positive rather than
    `0`–`1` because it multiplies a width: zero would mean a bin of no width,
    and a `0`–`1` scale could not express coarser bins at all. The archive
    study accepts `0.1`–`10`, so Historical Mode requests
    `max(bin size, 0.1)`; a finer live setting draws its historical zones at
    the archive's finest width.
  - The chosen bin size is saved with the indicator's preferences and restored
    on reload; a stored value outside the accepted range falls back to the
    default.

> **Changed 2026-09-25.** This field was previously _"Row size override
> (ticks)"_, an absolute tick count sent as `ticks_per_row`, and it has been
> **removed** in favour of the multiplier (`bin_size_multiplier` on the wire).
> A tick is not a unit of price movement, so an absolute tick count is not
> portable between instruments — the same number is a sensible row on one
> instrument and a degenerate single row on another. Sizing is now always
> derived from the instrument, with the multiplier as the only user control.
> Two consequences worth noting: a bin can no longer be pinned to an exact
> width independently of volatility, and because the multiplier scales a width
> that is then snapped to the cache grain, small multipliers can still be
> quantised away on coarse-tick instruments. The grain was **lowered 32 → 8
> ticks** on 2026-09-25 for that reason: at 32 the grain sat at or above both
> clamp bounds on `/ES`, so the clamp collapsed to a constant and every
> multiplier from 0.1 to 10 resolved to the same 8.00-point bin — the control
> did nothing. At 8 the same instrument offers 4.00, 6.00, 8.00, 10.00, 12.00
> and 14.00-point bins, and the finest reachable width is 2.00 points.
>
> Two limits still bind below that, and neither is the multiplier:
> `MAX_ATR_ROW_COUNT` caps the row count, and the grain is the absolute
> floor — one display row is never less than one grain, so the minimum bin is
> `grain × tickSize`. Changing the grain changes the meaning of every stored
> `price_bucket` (they are absolute grain indices), so the cache keys its
> invalidation on the grain as well as the tick size.

- **Row and bucket limits.** `MAX_ATR_ROW_COUNT` is
  `DEFAULT_TARGET_ROW_COUNT / MIN_BIN_SIZE_MULTIPLIER` (75 / 0.02 = 3,750).
  `MAX_PROFILE_BUCKETS` is 4,000, the same figure in the engine, the wire
  schema's `buckets.maxItems` and the browser parser; a contract test holds
  all three equal. A session with more buckets is merged by
  `rescaleSessionToFit` before it is sent. At that ceiling a live profile
  frame is about 450 KiB, sent on every 1.5 s poll.
- **POC.** The bucket with maximum volume; a tie breaks toward the bucket
  closest to the profile's price mid-range.
- **Value Area.** Expands outward from POC one bucket at a time — compare
  the next bucket above the current VA-high against the next bucket below
  the current VA-low, add whichever has more volume, repeat until
  cumulative Value Area volume reaches 70% of total.
- **Single prints.** A bucket under 15% of POC volume.
- **Aggressor classification.** Binance `trades.side`; dxFeed
  `dxfeed_time_and_sales.aggressor_side`. `UNDEFINED`-aggressor dxFeed trades
  count toward total volume but are excluded from the buy/sell split.
  Filtered to `event_kind = 'NEW'` and, for futures, `valid_tick = 1`.
- **Live period alignment.** The open period's own start is the same
  epoch-aligned boundary (`floor(now / periodMs) * periodMs`) the client
  uses for historical zones, so the live block and the historical chain sit
  on one shared grid with no gap or overlap.

## Sourcing and the rollup cache

Volume Profile reads exclusively from storage — it does not listen to a
live trade stream. An open period polls storage on a short cadence via
cursor-based incremental reads (only trades since the last poll); a closed
range (Fixed Range, a finalized period, a historical zone) is answered from
a per-minute, per-price-bucket rollup cache.

The rollup cache lives in its own SQLite file, separate from the trade
tables it derives from. The trade tables stay strictly read-only from the
server; the cache is disposable and rebuilds itself from storage on demand.
Coverage is tracked explicitly per instrument so a quiet minute is
recorded as covered, not mistaken for missing data on the next request.
Every display row width is an exact multiple of the cache's own grain, so a
historical zone answered from the cache is bucket-for-bucket identical to
the same window computed directly from the raw trade tables — proven by a
dedicated equality test, not assumed.

Historical zones for the visible chart range are requested in a single
batched message per pan/zoom settle, answered as one profile frame per
period from one grouped cache read, instead of one request per period.

Volume Profile does not stay live when the collector process is off, and a
profile can only cover trades since the collector started — no REST
backfill exists for raw trades on either provider. Both are accepted,
deliberate scope boundaries.

## Rendering contract

- POC line: solid while a period is closed, dashed while it is still
  developing (live only).
- VAH/VAL lines: same solid-while-closed, dashed-while-developing
  behaviour as POC — both bounded to their own period only, never
  extending across periods.
- Value Area (POC to VAH/VAL) fill is visually distinct from the outside-
  Value-Area fill; single-print buckets get their own distinct fill when
  the setting is on.
- Each bucket's bar length is scaled against **that profile's own busiest
  bucket** (`bucket.volume / maxVolume`) — not against any cross-period total.
  So bar length is comparable **within** one profile and carries no meaning
  **between** profiles: two adjacent historical zones whose total volumes
  differ tenfold both render a full-length bar at their own POC. This is the
  single most important interpretive limitation of the indicator. Read a
  profile's shape, not its absolute size against its neighbours.
- Bar width is capped at a fixed maximum, further capped to the zone's own
  on-screen width so a narrow zone's bars stay inside that zone instead of
  reaching into neighbouring periods.
- A Per-Candle zone's bars and fill render above the candle series; every
  other mode's bars render behind it, as background context.
- A developing (still-open) period renders at reduced opacity; a closed
  period renders at full opacity.
- A developing period is drawn against the pane's own edges: its anchor is
  clamped to the chart's left edge, and its POC/VAH/VAL lines run to the
  chart's right edge. Zooming or panning the session start off screen
  therefore keeps the live profile readable against the left edge instead of
  painting it off canvas at a negative x. Closed and historical zones keep
  their true timestamps and scroll away with their own session. This lives in
  `profilePeriodGeometry.ts` (`resolveProfilePeriodGeometry`) and is shared by
  Delta Profile and Net Delta Profile, which follow the same rule. Delta
  Profile draws net-sell bars left of its axis, so its floor is its bar budget
  rather than the pane edge (`anchorFloor: "bar-budget"`): a developing axis
  never sits closer to the left edge than the longest bar, and both halves
  stay on screen.

## Session Volume Profile: one indicator, three views

`sessionVolumeProfile` ("Session Volume Profile (Volume / Net Delta /
Delta)") is the one registered indicator. Its **View** input selects which
rendering draws the frame that is already arriving:

- **Volume Profile** (`volumeProfile`) — the volume-at-price bars below.
- **Net Delta Profile** (`netDeltaProfile`) — signed net-delta bars.
- **Delta Profile** (`deltaProfile`) — Delta Profile's own signed bars and
  in-bin values.

One frame, one session config, one palette, one legend row, one visibility
toggle. Changing the view re-draws the frame on the selected primitive and
requests nothing new from the host, because the view is a rendering choice
over the same `ProfileFrame` and the same `profile_config`.

- **Shared palette.** `buyColor`/`buyValueAreaColor` are the delta views'
  net-buying bar and the volume view's traded-volume bar (inside and outside
  the value area); `sellColor`/`sellValueAreaColor` are the net-selling bar or
  the volume bar's sell-side share; `pocColor`, `vahValColor`,
  `showPocLine`, `showValueAreaLines` and `vahValStyle` apply to all three.
  The defaults are Volume Profile's own former colours, so the volume view's
  default appearance is unchanged; the two delta views now start from those
  same colours instead of their own.
- **Value area percent** is offered only for the two delta views, which
  derive their levels client-side. The volume view's value area is the
  frame's own volume-based levels, as before.
- **Migration.** `sessionProfileSettings.ts` reads a workspace saved before
  the merge through to this id, once: the view is the legacy entry that had
  its own saved settings (a delta view priority, since only those carried a
  palette), `mode`/`periodMs`/`binSizeMultiplier` come from the legacy
  Volume Profile entry that owned them, the palette comes from that same
  chosen delta entry when there is one, the merged indicator inherits the
  favorite if any of the three was added, and it is hidden only if every
  legacy entry that recorded a visibility was hidden. The legacy keys are
  written out on the next save.

## Net Delta Profile

Net Delta Profile (`netDeltaProfile`) draws each bucket of the same
`ProfileFrame` as one signed bar of `buy_volume - sell_volume`. It is the
`netDeltaProfile` view of Session Volume Profile, so it shares the one
session and binning configuration that indicator exposes: the View dropdown,
mode, session length and bin size all live in that single settings object,
so one server profile config drives every profile overlay. Its own half of
the palette is the buy/sell pair, the delta POC and value-area toggles, the
value area percent and the VAH/VAL line style.

- **Delta POC.** The bucket with the largest `|buy_volume - sell_volume|`; a
  tie breaks toward the bucket closest to the profile's price mid-range, then
  toward the lower price.
- **Delta value area.** Expands outward from the delta POC over the buckets
  the frame carries, adding whichever neighbour has the larger `|delta|` until
  the cumulative `|delta|` reaches the "Value area percent" share (0.1 to 1.0
  in 0.05 steps, 0.7 by default) of the profile's total. A price row with no
  trades is not in the frame, so the expansion steps over it; the server's
  volume value area instead walks every price row and counts an empty one as
  zero. The frame's volume-based `poc_price`/`vah_price`/`val_price` are not
  used by this indicator.
- **Labels.** The chart labels read "Δ POC", "Δ VAH" and "Δ VAL", and the
  settings name them delta levels, so a bare "POC" on this terminal always
  means the volume POC.
- **Bars.** Every bar grows right from the zone's left edge: net buying in the
  buy colour, net selling in the sell colour, length `|delta| / maxAbsDelta`
  of the zone's bar-width budget. A bucket that nets to zero draws nothing.
  Bins inside the delta value area use a brighter tint and an opacity band of
  0.8 to 1.0; bins outside use 0.35 to 0.7. Both bands grade with `|delta|`.
- **In-bin values.** Each bin prints its signed net delta, left-aligned,
  sized to the box and skipped when the box cannot hold 7 px text. The ink is
  near-black or white, whichever has the higher WCAG contrast against the
  bin's fill composited over the chart's own background. Across the default
  palettes, every alpha and both chart themes, the chosen ink is at least
  4.45 : 1.
- **Layering.** Bars draw above the candle series in every mode, and above the
  POC/VAH/VAL lines.
- **Line style.** The delta POC is solid when closed and dashed while
  developing; VAH/VAL use the chosen style (solid, dashed or dotted). The
  style is saved and restored with the other preferences.

## Provider provenance and limits

- **Binance:** tick size fetched from `exchangeInfo`, cached with a daily
  refresh; falls back to the last-cached value on a fetch failure.
- **dxFeed (futures and equities):** tick size is read from the governed
  instrument catalog, `config/market-instruments.json`, validated at module
  load so an unconfigured instrument stops the process rather than silently
  disabling Volume Profile and VPIN. `instrument-tick-size.js` resolves it
  through `tickSizeFor` in `dxfeed-config.js`.

> **Corrected 2026-09-03 (`L1L2-V2-066`).** This previously said dxFeed tick
> sizes were "hardcoded at `0.25`" for futures and "`0.01`" for equities. Phase
> 1.1 (`L1L2-V2-010`) deleted both hardcoded lists and moved the values into the
> catalog, precisely because `config/README.md` forbids a server-local
> instrument list. The doc pointed a reader at code that no longer existed, and
> presented a governed configuration value as a hard limit. The underlying
> values are unchanged (`/ES` and `/NQ` are still 0.25, equities 0.01) — what
> changed is that they are now configuration, not constants.

`ProfileFrame` (`type: "profile"`) carries `mode`, `period_start_ts`,
`period_end_ts` (`null` while developing), `row_width`, a bounded
`buckets` array (`price`, `volume`, `buy_volume`, `sell_volume`,
`single_print`), and `poc_price`/`vah_price`/`val_price`. One frame type
serves both a live update and a historical zone.

## TA.04 migration

Unlike Killzones, the generic settings system (`SettingsFieldSchema`'s
`tab`/`radioGroup`/`numeric`/`visibleIf`, rendered by
`GenericIndicatorSettingsBody`) turned out to be a clean, already-built
match for this modal's tabs and conditional fields — no new SDK capability
needed, apart from one small, genuinely reusable addition:
`GenericIndicatorSettingsModal` gained an optional `defaultSettings` prop
that renders a "Reset to default" footer button (every prior bespoke
modal, including this one, already had one; the generic modal didn't).
**Disclosed side effect, not scope creep left unnoticed**: this addition
went into the one _shared_ modal loop every `settingsSchema`-driven
indicator in `MainPanel.tsx` already uses, so RSI/EMA/SMA/`largeTradeBubbles`
(none of them touched by this ticket) also gained a working reset button
they never had before, not just Volume Profile getting its old one back.
A strict, uniform UX improvement, not a regression — but named here
explicitly rather than left as an unremarked side effect of an
unrelated ticket's fix. Covered by a real test using `smaIndicator` as
its fixture (`GenericIndicatorSettingsModal.test.tsx`), proving the
button is generic, not Volume-Profile-specific.

One real design decision, not a code accident: Volume Profile and Delta
Profile share the exact same `mode`/`periodMs`/`binSizeMultiplier` session
config today (both settings modals edit the same underlying value). The
SDK's settings model is one `T` per indicator with no "shared between two
indicators" concept, so a naive migration would have let a user set each
indicator to a different session independently — a real, visible
behavior change. Decided explicitly: keep them synced. Only
`volumeProfileIndicator` owns this config in its `settingsSchema`;
`deltaProfileIndicator` has no schema of its own (giving it one would
render a second, competing generic modal alongside its existing bespoke
one) and instead reads/writes the shared config through
`volumeProfileIndicator`'s settings object. Proven directly: a dedicated
test changes mode via Delta Profile's own modal and asserts Volume
Profile's legend detail reflects it; mutation-tested by breaking the
write-through and confirming the test fails.

> **Superseded 2026-10-03.** The write-through above was a workaround for two
> registrations sharing one dataset. With the three views merged into
> `sessionVolumeProfile` there is one settings object and one modal, so the
> write-through, both bespoke modals and the per-view visibility paths are
> gone; `sessionProfileIndicator.tsx` carries the config directly. The
> "kept them synced" decision itself stands — one session config still drives
> every profile drawing, now by construction.

The bin-size multiplier is a plain `number`, so it originally used the
schema's `custom` field kind: it is a float with a range and, since the
absolute override was removed, no blank/"auto" state at all.

> **Changed 2026-10-03.** It is the schema's `slider` kind now — `min` 0.02,
> `max` 10, `step` 0.01, the same bounds `isBinSizeMultiplier` enforces — with
> the field's ATR explanation kept as a `staticHint` beneath it, and the
> bespoke `VolumeProfileBinSizeMultiplierField` deleted. One consequence of
> the built-in slider, whose persistence validation requires the value to sit
> on its step grid from `min`: a hand-typed off-grid value from the old number
> input (e.g. `0.035`) falls back to the default on load rather than
> surviving. Values the UI can produce are all on-grid.

One named, deliberate, harmless behavior difference: the generic
`radioGroup` renderer sets `name={field.key}` (e.g. `"mode"`) rather than
the old modal's hardcoded `name="volume-profile-mode"`. Radio grouping
still works identically; only an internal DOM attribute value changed,
invisible to any real user. One existing test's selector was updated to
match.

## Verification obligations

Deterministic tests must prove: POC/Value-Area correctness against hand-
built reference cases (symmetric and asymmetric expansion, POC tie-break);
row-width resolution on both a high-priced and low-priced instrument;
cursor-paginated incremental application producing the same result as a
fresh full aggregation over the same trades; rollup-cache buckets, POC,
Value Area, and single prints matching a raw scan exactly, at multiple row
widths; batched historical-zone requests answered as one frame per period
with no partial-period range ever sent; `UNDEFINED`-aggressor dxFeed trades
excluded from the buy/sell split while still counted in total volume.

For Net Delta Profile, deterministic tests must prove: the delta POC lands on
the largest `|delta|` bucket, including a net-sell bucket and both tie-break
rules; the delta value area grows to the chosen share; bar length is `|delta|`
against the profile's own `maxAbsDelta`; a zero-net bucket draws no bar; the
chosen in-bin ink is never the lower-contrast one; the View dropdown selects
one of the three renderings without asking the host for a new config; a
workspace saved before the merge is read through to `sessionVolumeProfile`
with its session config, chosen view and palette intact; the bin size and
line style survive a reload; and Historical Mode never requests a bin size
below the archive's floor.

Before release, retain separate live Binance and dxFeed screenshots or
replay evidence showing all three modes, developing-vs-closed styling, and
historical zones rendered alongside the live period, for the volume and
net-delta views.
